# Диагностика соединений через MCP: пробелы и план (разбор 2026-10-24)

Цель владельца: ИИ-агент с токеном MCP только на чтение понимает соединения каждого клиента — где какой протокол на какой ноде плохо работает, где ложное срабатывание, а где реальная блокировка, — чтобы у всех было стабильно и быстро; панель должна стать стандартом уровня 3x-ui/Remnawave и быть лучше. Разбор: opus-plan по коду ветки feat/node-journal и живым данным флота 23–24.10; основные ссылки проверены основной сессией. Продолжение `connection-diagnostics.md`.

## 0. Главное

1. **Баг Hysteria2 (подтверждён по коду).** Сессия запоминается по адресу клиента (`internal/node/hysteria2/index.go`, `Connect`), а ядро сообщает отключение с текущим адресом: подключение — `h.conn.RemoteAddr()` (hysteria core v2.12.3 `server/server.go:214`), отключение — `conn.RemoteAddr()` (`server.go:137`); при `DisablePathManager: true` (`server.go:65`) форк quic-go меняет адрес по первому пакету с нового адреса (`apernet/quic-go … connection.go:1291-1293`). С port hopping адрес долгой сессии меняется постоянно: `Disconnect` промахивается, обрыв не считается, `cs.conns` не уменьшается, сессия-призрак остаётся «онлайн» до перезапуска инбаунда — завышены `online_s`, онлайн, неверны токены kick.
2. `drops` Hysteria2 не отличают заморозку ТСПУ от проверок клиента без доступа к `*quic.Conn`; публичный API ядра его не даёт. Правка форка (~15 строк: `ConnOpened/ConnClosed` в `serverImpl.handleClient`) даёт «сервер слал в пустоту» против «обе стороны молчат», RTT и потери, счётчик завершённых рукопожатий.
3. Без форка достижимо: тип закрытия по `err`, hellos по своему/чужому SNI, нерасшифрованные пакеты AWG userspace, почасовой `udp_rx_packets`, `stall_s`, пиковая скорость устройства.
4. Дешевле всего и полезнее — только панель и MCP на существующих данных: разрез по приложению (`device.client`), почасовые ряды, сводка по флоту, честные описания полей.
5. Алерт «drops» о людях из §6 при живых числах (de 76 %, be 56 %) сработал бы на каждого пользователя Happ — убрать до классификатора заморозок.

## B. Различающие сигналы (ложное срабатывание или блокировка)

Хранение — новые столбцы `link_hour` в том же `INSERT … FROM json_each` (+0 statement); протокол — аддитивные поля LinkCounters и `links/2`.

- **B1 H2 короткий обрыв по idle.** Без форка (S1a): исправить ключ сессий (`Disconnect` получает id: при промахе искать сессию этого ключа — с тем же IP, иначе самую старую; промах считать в `addr_changes`); тип закрытия по `err`: `nil` — клиент закрылся (`client_closes`), `ApplicationError` local — наш kick, `StatelessResetError` — клиент забыл соединение, `IdleTimeoutError` — тишина; `quiet_drops` — drop < 8 КиБ за сессию (одна крошечная проверка); `drops − quiet_drops` ≈ «8–64 КиБ и тишина» (похоже на заморозку; для QUIC — предположение). С форком (S2): `ConnectionStats()` в Collect раз в 10 с; при idle-закрытии `PacketsReceived` не рос, а `PacketsSent` рос → `freezes`, иначе `quiet`; байты сессии — из соединения.
- **B2 H2 hellos без auth.** S1a: `hellos_foreign` — SNI ClientHello не наш (сканеры). S2: `accepted` (дошли до Accept, QUIC+TLS завершены): `hellos_ours − accepted` — рукопожатие не завершилось (DPI/прерывание), `accepted − handshakes` — без auth (пинги приложений, маскарад). Тип ошибки рукопожатия дёшево не получить. Скачок после смены cert_pin — сверка на панели.
- **B3 AWG stall.** userspace добавляет к rx только принятую инициацию (148 байт, `amneziawg-go device/receive.go:425-426`), ответчик засчитывает рукопожатие по первому пакету с новыми ключами (`receive.go:511-513`): stall = нода ответила, клиент не подтвердил. S1b: `stall_s` (реальная длительность), инициации ≈ Δrx/148. Различители на панели: то же устройство на других профилях ноды, другие устройства на профиле, `device.client`/`awg_version` застрявших ключей (одно приложение → `client_incompat_suspected`), синтетика.
- **B4 AWG «ничего не видно».** S0: udp_rx_packets и reported_unix в MCP; S1b: почасовой `udp_packets`; userspace `Verbosef`: «unknown type» (неверные H/S или мусор Jc/I), «invalid mac1» (обфускация верна, ключ сервера не тот) → `unparsed_excess`, `bad_mac1`. Дерево: udp_packets не рос → потеряно в пути (дальше node_ports); рос + unparsed/bad_mac1 → конфиг/версия клиента; рос + stalls → B3.
- **B5 VLESS (фаза 3).** TCP_INFO (поля есть в x/sys), плюс `ECONNRESET` при малом Bytes_received → `resets`; XHTTP/WS через CDN помечать.
- **B6 Нода/хостер/хост панели/ТСПУ** — сигналы есть, их должны подтягивать находки (D).
- **B7 «Пачка проверок»** — на панели по link_hour: устройство за час коснулось ≥ 3 инбаундов, на каждом ≤ 2 подключений, ≥ 80 % тихих → находка `client_checks` («безвредно»), не алерт.

## D. MCP

Исправить в S0 вводящее в заблуждение: описание drops («idle-закрытие в первые 60 с или до 64 КиБ: заморозка или короткая проверка клиента; само по себе не признак блокировки»), stalls (раунды → stall_s), hellos (сканеры, пинги, PSK), online_s, нули неподдержанного → `unsupported`, kl!ck без задержек. Добавить: `fleet_connections` (нода × профиль × протокол с долями и находками, одно чтение), `by_hour`, `clients` (по приложению/версии/платформе) в node_connections, client/platform/kind в строках user_connection, блок `awg` (udp_rx_packets, backend, онлайн-пиры), `findings[]` {kind, subject, evidence, cross_checks, confidence, next_step} — одна функция в internal/panel/health, общая с алертами и UI. Отдельный connection_diagnosis не нужен.

## E. Алерты (фаза 4), всё в Info на первый релиз

- Люди: убрать `drops`; `freeze` (после S2/S3: freezes ≥ 3, ≥ 50 % сессий ≥ 4 КиБ, ни одной ≥ 10 мин; держится freezes ≥ 1 за час); `rejected` как в дизайне; AWG `handshake`: stall_s ≥ 600 за 2 ч, ≥ 2 × онлайна с трафиком, в каждом часе ≥ 120.
- Инбаунд: H2 до S2 — Info по (ours − handshakes)/ours ≥ 0.7; после S2 — ours ≥ 20 в обоих часах и 1 − accepted/ours ≥ 0.5, синтетика зелёная, ≥ 2 ключа с подключениями. AWG — keys_stalled ≥ 2 и ≥ 50 %, у ≥ 2 людей и в ≥ 2 разных приложениях/версиях (иначе находка client_incompat_suspected). AWG unparsed — udp_packets ≥ 600/ч два часа при нулевых инициациях. VLESS — (freezes + stalls)/accepted ≥ 0.5 при accepted ≥ 30 и ≥ 2 людях.
- Защиты: объём и два часа подряд, ≥ 2 человека для инбаунда, вытеснение check_failed/node_down/udp_loss, 20 мин тишины после рестартов и обновлений, устройства с client_checks не учитываются, одно приложение → находка, 2 ч без данных → закрытие.

## G. 3x-ui и Remnawave

- 3x-ui (Xray): трафик по клиенту, онлайн, лимит IP через access-log и fail2ban (хранит IP), Telegram (входы, CPU, сроки, трафик); диагностики блокировок нет.
- Remnawave: лимит устройств по HWID, события user.first_connected/not_connected, node.connection_lost/restored, traffic_notify, torrent_blocker в Telegram и вебхуки; плагины ноды (torrent blocker, фильтры, списки IP); Prometheus-метрики, ASN в плагинах (2.8.0); модуль connections с экспортом соединений в Redis Streams (3.0.0).
- Где они впереди: история и временные ряды (у нас — нет истории по ноде; S1b закрывает часть, `/metrics` — отдельно), вебхуки по событиям (вне плана). Списки IP по человеку сознательно не копируем.
- Где мы выигрываем: ни одна не объясняет, почему у конкретного человека не работает — блокировка, клиент, нода или хостер — по протоколу и без хранения IP; нет точки наблюдения в стране и диагностирующего агента через MCP; нативного AmneziaWG у них, насколько видно, нет. S0, S1 и S4 с находками — продуктовое преимущество.
