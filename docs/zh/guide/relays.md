**中转**是某个节点（**入口**）上的一个端口，它把另一个节点（**出口**）上某个服务器的加密流量原样转发过去。网络封锁了出口地址的用户，只需连接入口：入口把他们的数据交给出口，其余一切仍由出口完成。途中不会解密任何内容：会话依旧是从用户的手机直达出口。

入口节点用内核转发（一张它自己的 `nftables` 表 `mistgate_relay`，每条中转一条 DNAT 规则），因此几乎不占用 CPU 和内存。入口上没有被中转服务器的任何密钥。例外是出口只能通过 IPv6 到达的中转（见下文「路径的地址族」）：内核无法把一种地址族的包改写成另一种，入口会像桥一样在用户空间承载它。

## 什么时候有用

| 用户遇到的封锁 | 经中转 |
|:--|:--|
| 出口的 IP 地址或子网被其运营商或所在地区封锁，而国内其他地方能访问 | 有用。用户连接入口的地址；入口从自己的数据中心访问出口。 |
| 连接境外托管商的流量在几 KB 后冻结（主要是移动运营商） | 如果入口所在网络不在该名单上，且入口到出口的链路不冻结，则有用。 |
| 移动网络的白名单：只放行获批的地址 | 只有当入口的地址本身在名单上才行。普通 VPS 通常不在其中；在承诺任何事之前先检测。 |
| 出口 IP 在全国范围内被封锁，包括入口所在的数据中心 | 没用：入口到出口的链路同样被封。开启前的检测会发现这一点。 |
| 入口也被过滤（它的地址、它托管商的地址段） | 没用：用户连不上入口。入口节点自己在**可达性**中的国家检测会显示这一点。 |
| 协议在整条路径上都被切断 | 没用：中转传递的是同一个协议，同样会被切断。 |

所以中转针对的是**按地址或按网络、而不是按国家**的封锁，并且要求用户能够连上入口。选择之前，对话框会给出三条提示：国家检测如何看待出口、入口能否访问出口（当 [TSPU 探测](../operations/reachability.md#tspu-探测)从该入口运行时才知道），以及用户能否连上入口。「无数据」表示未知，不表示没问题。

## 入口所在国家能看到什么

- **能看到**：连接的用户的地址（那里的家庭和移动线路与个人绑定）、时间、流量大小，以及出口的地址。
- **看不到**：网站、内容和密钥。会话从手机到出口全程加密。入口自身的运营商看到的与任何运营商一样：与某个地址的连接。
- **入口被查扣**时，能得到「端口 → 出口地址」这张表，以及该节点为它自己的服务器保存的内容。上面没有任何用户去向的信息。

位于审查国家的中转受该国法律管辖：其托管商可能需要识别你的身份，并提供对服务器的访问。中转能看到地址和流量大小，看不到内容。托管商也可能关闭服务器；中转可以一键移除，入口上也没有用户访问去向的记录。这不是法律意见：请自行判断入口所在国家对你和你的用户是否可以接受。

## 工作方式

1. 你选择另一个节点的服务器，以及入口上的端口（默认使用出口自己的端口，前提是它在入口上空闲）。
2. 面板检测**链路**：入口节点尝试连接出口的服务器（TCP 端口必须表现为 Mistgate 自己的服务器；UDP 则由出口统计收到的数据包）。
3. 开启中转：入口的 Agent 安装转发。
4. 面板检测**路径**：第三个节点（不是入口也不是出口；只有没有其他节点可用时才用面板本身）**经由入口的端口**访问出口的服务器。
5. 只有这时中转才是「正常」，订阅里才会出现第二个服务器。任一检测未通过的中转会被再次关闭，对话框会说明停在哪个阶段。

这样用户会同时拥有节点自己的服务器和经入口的服务器。如果只想给他们经入口的服务器，请在出口节点**入口**选项卡的**直连**中，于**订阅中**关闭该服务器（参见[节点](nodes.md#直连)）：它仍会为中转运行。

计费仍留在出口：流量、配额、限速、设备和[种子保护](torrent-protection.md)照旧按每个人生效。出口看到的是入口的地址，而不是用户的地址。流量会两次经过入口（来自用户和发往出口），因此入口的流量限额和负载两个方向都计入；延迟是用户到入口加上入口到出口。由内核转发时 MTU 不变；在用户空间承载的 IPv6 路径会把每个 UDP 数据报经另一种地址族重新发送，因此该段 MTU 更小时会表现为丢包，直到客户端的 QUIC 自行调整。

## 添加中转

1. 如果**更新**页面提示，请先更新入口节点的 Agent：旧版 Agent 不能转发（「msk1 的 Agent 版本过旧，不支持中转。请在更新页更新。」）。服务器的防火墙必须放行被转发的流量；如果它丢弃这类流量（`FORWARD` 策略为 `DROP`，UFW 和 Docker 默认如此），中转无法工作，该行会说明。
2. 打开用户访问不了的节点：**节点** → 该节点 → **入口**。节点在检测所用的国家无法访问时，列表上方会有按钮**让它在俄罗斯可访问…**。列表下方的**添加入口…**会打开同一个窗口，灰色的**经由其他节点**行（「备用路径，以防该节点无法直接打开」）也一样。[IPv6 入口](nodes.md#ipv6-入口)有自己的按钮：**添加 IPv6 入口…**。
3. 窗口**让它在俄罗斯可访问**分四步：**节点**、**入口**、**用户将得到**和**完成**。在**节点**一步，你来自的节点已经选好，并带有判断：「已有可用路径，再加一条备用」、「部分可用」或「没有路径」。点击**下一步**继续。
4. 在**入口**一步选择用户要经过的节点（「用户应经由哪个节点访问 de1」）。标有**合适**的节点排在前面；每个节点显示国家检测如何看它、它能否连到 de1（在 TSPU 探测从它运行的情况下）以及它的负载。已经在中转 de1 服务器的节点不会再次出现：要增加服务器，请用它那一条入口里的**让更多服务器经此…**。与出口同国家的入口对用户没有帮助，因为他们到它的路径不变：它永远不会标为**合适**，带有「与出口在同一国家」的提示，但仍可选择。
5. 在**用户将得到**一步勾选要中转的服务器。每行显示协议配置及其在入口上的端口（「msk1 上的 tcp/443」）；无法中转的服务器显示为灰色并注明原因。端口由面板选择：出口的端口（若在入口上空闲），否则用一个空闲端口；之后可在服务器菜单里用 **更换端口…** 修改。列表下方，窗口会说明谁将得到什么（「12 位用户将得到“DE · 经 RU”：3 个服务器，经 msk1，与原有的并存」）。如果直连连不到出口、但出口能连到入口，窗口会写「将经桥接」。**检测并开启**开始运行；**返回**回到选择入口。
6. **完成**一步显示运行进度（「检查并开启 · 1 / 3」）和每个服务器一行（「正在检查 msk1 → de1 和外部访问」，然后是「正常」）。对每个服务器都会运行[工作方式](#工作方式)中的两项检测，两项都通过才会开启中转。**停止**会让正在处理的服务器完成，不再处理后面的。可以关闭窗口：运行会继续，结果在**入口**标签页里（已创建但未开启的中转显示为「尚未完成」，带按钮**继续完成**）。失败的服务器保持关闭，不会给用户任何服务器；如果它的端口被占用，该行会提供**使用 8444**，**其他入口…** 则换一个节点重新开始。最后会显示：「de1 可经 msk1 访问。用户将在下次订阅更新时获得新服务器。」
7. 每个服务器的行显示**正常**、**已关闭**、**故障**、**正在开启…**或**检测中…**。正常的一行会写客户端看到的情况（「客户端视角：182 ms · 3 分钟前」）；故障的一行会写原因（链路：「自 14:20 起故障：msk1 无法通过 443/tcp 连到 de1。」；路径：「从外部无法访问 msk1 上的 443/tcp」，即入口的防火墙或托管商，或 `FORWARD` 被丢弃）。该行的 **⋯** 菜单有**立即检测**、**开启**或**关闭**、**更换端口…**、**方式…**和**移除…**（会问「确定移除？」）。**开启**需要 15 分钟内通过的检测。

面板无法证明属于本节点的服务器只做力所能及的检测：Fake TLS 回落到其他网站的 [MTProto](mtproto.md) 服务器没有本节点的名称可用于检测。该行会显示「已开启。面板无法检测：服务器没有可用于检测的名称」而不是失败，仍然可以开启。Fake TLS 回落到节点自己网站的 MTProto 服务器会像 VLESS 一样检测。

也可以从入口一侧开始：入口节点 → **入口** → **为谁转发** → **转发更多节点…**会打开**节点**页的**路径**视图，那里的按钮会启动同一个窗口。

在出口节点上，每条中转是**入口**标签页里的一个入口**经 msk1**；在入口节点上，它是**为谁转发**中出口对应的一行。从节点上删除协议配置，或让节点退役，也会删除依赖它们的中转；对话框会告诉你有几条。

## 监控

每条开启的中转都会作为单独的目标加入客户端视角检测轮次：面板像应用一样，经入口的转发端口、使用出口的协议配置和凭据建立连接，并通过它读取 64 KB，因此开始后又停止的传输会被算作冻结。

- 中转行显示最近一轮的结果：「客户端视角：182 ms · 4 分钟前」，或失败的阶段（「经中转：传输在最初几 KB 后停滞，4 分钟前」）。
- 它还显示自入口 Agent 安装转发以来经转发通过的字节数和数据包数，以及 Agent 读取的时间。没有计数器的旧版 Agent 不显示这些。
- 连续两轮失败后，[运行状况](../operations/health.md)页面会出现 `relay_down` 告警：「经 msk1 的 de1 中转不可用」。告警用文字说明所处阶段：`leg`，入口连不上出口；`entry`，入口上的转发没有安装；`path`，从外部经入口没有任何流量通过；`freeze`，传输在最初几 KB 之后停滞。告警上的**打开入口**按钮会打开出口节点的**入口**标签页，并定位到该入口。
- 出口自身的检测告警或任一节点的 `node_down` 未关闭时，该告警让位于它们；中转恢复正常后自动关闭。Telegram 也会发送它。

面板自己的检测从面板所在的服务器发起，位于入口所在国家之外，因此它们能发现链路中断或面板这条路径上的停滞，但发现不了 TSPU 对国内用户施加的冻结；对此请查看[可达性](../operations/reachability.md)中的 bsbord 和 kl!ck 报告。

## 桥接：入口连不上出口时

转发中转（**转发**，下文称直连）只朝一个方向工作：入口主动连接出口。有些过滤器会切断这个方向的连接，却放行出口主动连向入口的连接。**桥接**正是利用这一点：出口连接入口，并保持几条加密连接不断开。用户连到入口的端口时，入口把他的会话交给其中一条连接，由出口接收。入口不打开会话，这一点和直连中转相同。

桥接只承载 TCP。

每条中转的方式都可以单独设置：该行 **⋯** 菜单里的**方式…**，或配对（入口和出口一起）**方式**区块里的**方式：自动**按钮。只有所有者可以更改；更改时用户已打开的连接会断开，应用会自动重连。

| 方式 | 作用 |
|:--|:--|
| **自动（推荐）** | 转发可用时走转发。入口连不上出口时，面板会自动切换到桥接，直连恢复后再切回来。 |
| **仅转发** | 入口连接出口。不会自动切换。 |
| **仅桥接** | 出口连接入口并保持连接。不会自动切回：只有你能更改。 |

**哪些能通过桥接：**

- **VLESS over TCP**（Vision 与 XHTTP）：可以。
- **MTProto**：在第一版之内，但真实流量下尚未验证。在测试环境中，一台有自己网站的服务器显示直连路径已断、桥接已建立，但面板仍拒绝切换到桥接：节点网站使用的是自签名证书，而路径检测需要可以验证的证书（测试环境中没有 Let's Encrypt）。Fake TLS 回落到其他网站的服务器无法使用桥接：面板无法检测其路径，会干脆地拒绝。Telegram 自身的流量经桥接传输的情况尚未测试。
- **Hysteria2 和 AmneziaWG**（UDP）：只能直连。把 UDP 放进 TCP 连接中会损害 AmneziaWG，并破坏 Hysteria2 自身的拥塞控制，因此面板不为它们提供桥接。

**「自动」如何切换：**

- **切到桥接。** 面板大约每 10 分钟检查一次每条中转。连续两次失败即切换：入口连不上出口，或传输在最初几 KB 之后停滞。切换需要桥接已建立，且出口能连到入口。若桥接无法保持，会打开 `relay_down` 告警，阶段为 `bridge`。
- **切回直连。** 每 30 分钟，面板用一个简短的数据包测试检查直连路径。连续三次通过，且间隔至少 30 分钟、距上次切换也至少 30 分钟，之后进行一次数据流测试：入口打开到出口的连接，出口回送 8 MB。通过则切回直连；未通过则留在桥接，计数从头开始，下一次数据流测试至少 6 小时后进行。切回至少需要一小时。
- **切回后很快又出问题。** 切回直连后 30 分钟内，一次失败就足以切回桥接。
- 配对会显示进度，例如「转发在 14:20 不通。连续 3 次检查成功并通过测速后切回转发（当前 2 / 3）」。
- 每次切换都记录为事件，不发送 Telegram 消息。
- 切换会断开用户已建立的连接，应用会自行重连。

**桥接的负载：**

- 桥接保持几条连接，用户共享它们。每条连接约承载 120 人：两条连接约 240 人，四条约 480 人。
- 面板从两条开始。当桥接达到两条连接上限的 80%（约 190 人），或中转流量达到 10 Mbit/s 及以上时，面板会自动升至四条。若 30 分钟内没有理由保持四条，且使用人数少于约 100 人，则降回两条。
- 桥接行显示 **已用：N/约 容量**；达到 80% 时显示 **接近满载**。这只是提示，不发告警，也不发 Telegram 消息。
- 四条连接时桥接无法再扩容。新用户会被拒绝：一秒内找不到空位，他们的应用会改连其他服务器，桥接行显示 **已达上限**。此时可以用 **为 {出口} 选择其他入口…** 添加第二个入口，由它分担用户。

**测速检测：** 面板的 **测速检查（8 MB）** 按钮让出口向入口发送 8 MB，计入两个节点每天的测速次数上限。测试走入口的另一个独立端口，而不是桥接端口：它说明线路能撑住数据流，但不检测桥接本身。

**出口连不上面板时：** 出口的 Agent 会通过桥接连接，并在那里保持管理会话。到面板的加密是端到端的，入口只看到加密字节。在桥接上时，Agent 约每 10 分钟测试一次直连路径，连续两次成功即切回直连。重启后，Agent 先尝试约 50 秒直连。

Agent 的更新不经过桥接。位于桥接上的出口会从 GitHub 或 Cloudflare 更新（前提是面板提供这些来源；默认提供 GitHub）。如果只启用了 `panel` 来源，在到面板的直连路径关闭期间，这样的出口无法更新。

**第一版的限制：**

- **只支持 TCP。** UDP 服务器仍然直连。
- **出口看到的是自己的 Agent，而不是用户。** 经桥接的连接中，出口看到的是其 Agent 的地址，因此这些连接的网络（ASN）和日志不准确。流量、配额、限速、设备和 [BT 下载拦截](torrent-protection.md)仍按用户（密钥）正常工作。面板会将这些连接标记为 **经桥接**。
- **两个节点都需要新版 Agent。** 如果其中一个较旧，面板会指出需要更新的节点，中转保持直连。
- **在测试环境中验证，未在真实网络中验证。** 测试环境模拟了过滤器，说明逻辑正确，但不能说明真实过滤器会如何对待桥接。尚未验证：超过一天的会话；真实的 Mihomo 和 Telegram 客户端；旧版本 Agent；节点自有网站上的 VLESS 以及带 TLS 的 VLESS（两者都需要 Let's Encrypt 证书）；四条连接时的第二个入口；出口与入口以不同方式连接面板的情况。

## 订阅里的第二个服务器

每条正常的中转，会让用户在订阅中紧接着出口的服务器得到一个**副本**：密钥、SNI 和证书指纹都相同，地址换成入口的地址，端口换成中转的端口。名称以入口的国家代码结尾：`🇩🇪 DE · VLESS · via RU`（俄语订阅中是 `через RU`，中文订阅中是 `经 RU`），并按 Happ 的 30 字符限制压缩。所有格式都有它（链接列表、Mihomo YAML、Xray JSON、sing-box JSON）；在 Mihomo 分组里，它是同一个选择器的又一个选项。

- **谁会得到**：所有可以使用出口服务器、且可以使用入口节点的用户。没有新的设置；可以通过用户的节点选择来限制。
- **何时**：订阅下一次刷新时（默认每 12 小时）。已关闭或出故障的中转没有副本。
- **用户看到什么**：一个可选的第二个服务器，第一个连不上时可以用它。他们正在使用的服务器不变。
- **MTProto**：中转同样可以转发 [MTProto](mtproto.md) 服务器。副本不在订阅中：它是用户 **Telegram 代理**区块中的又一条链接，标记为 **经 RU**，密钥和握手中的名称与出口的相同。
- **TrustTunnel**：中转只通过 HTTP/2 转发 [TrustTunnel](trusttunnel.md) 服务器：副本只有 TCP，提供给 Mistgate 应用，不会进入 `tt://` 链接。

## AmneziaWG 经中转

中转转发 [AmneziaWG](amneziawg.md) 服务器的方式与其他服务器相同：入口转发它的 UDP 端口，隧道仍由出口维护。唯一的区别是密钥。出口为每个密钥只记一个地址，所以同一个密钥同时走两条路径，会让出口在两者之间来回跳变并丢包。因此，所有被允许使用出口服务器和入口节点的人，都会得到**一个只用于经入口这条路径的密钥和隧道地址**；直连服务器仍用它自己的密钥。

- **使用订阅链接的应用**（Mihomo 应用、Mistgate 应用）：经入口的服务器 `🇩🇪 DE · AmneziaWG · 经 RU` 会在订阅下次刷新时出现在直连服务器之后。应用此时获得它的密钥，无需任何操作。
- **AmneziaVPN 密钥：** 经入口的路径是单独的一份配置。它在设备卡片中（**显示密钥**，**节点**列表：「de1 · 经 RU」），也在用户的订阅页面上。需要把它作为新服务器导入 AmneziaVPN；直连配置保持不变。
- **设备：** 经入口的密钥不占用设备上限中的名额。
- **端口：** 默认情况下，入口先尝试适合该协议配置样式的端口（QUIC 为 443），前提是入口可以使用它；然后是出口的端口，最后是任一空闲端口。中转的端口更改后，需要重新下载 AmneziaVPN 配置。
- **删除：** 删除某服务器经某入口的最后一条中转后，该路径的密钥会自动吊销。
- **出口看到什么：** 这些用户来自入口的地址。
- **历史：** 在用户的连接历史中，此类密钥的行带有「经 RU」标记。

链接列表（URI）中没有 AmneziaWG 服务器：该格式无法承载它。

## 无法转发的服务器

| 服务器 | 原因 | 怎么办 |
|:--|:--|:--|
| CDN 之后的 VLESS | 用户连接的是 CDN，不是节点。 | 不用处理：它不需要中转。 |
| Let's Encrypt 证书签发给节点 IP 地址的服务器 | 应用会拒绝入口上的这个地址。 | 改用域名证书，或带指纹的自签名证书。 |
| 带端口跳跃范围的服务器 | 中转只传递一个端口。 | 副本只使用这一个端口：端口跳跃不能经中转使用。 |

## 路径的地址族

用户始终像现在这样连接入口。只有入口到出口这一段可以改变地址族：在中转行 **⋯** 菜单的**地址族…**（或 `relay` MCP 工具中的 `leg`）里设为**自动**、**IPv4** 或 **IPv6**。

- **自动**（默认）使用 IPv4，并在 IPv4 路径失效时自行切到 IPv6——最多每半小时切换一次，且只有在 IPv6 路径通过检查后才保留。IPv6 失效时同样切回。手动指定的地址族永不自动改变。
- **IPv6** 使用出口的 IPv6 地址：开启了 **IPv6 入口**时用该地址（它已通过外部检查），否则用医生为出口上行链路列出的第一个稳定地址。路径检查会证明这个入口能到达该地址和服务器自己的端口；如果出口没有这样的地址，检查以 `no_ipv6_address` 失败，不会安装任何东西。
- 出口不需要任何改动：它的服务器本来就监听所有接口，自己的 IPv4 仍然把用户带到互联网。入口在直连方式下需要可用的 IPv6，并且它的代理必须列出 `relay-forward/2`（旧代理无法承载这段路径，请在**更新**页升级）。在反向方式下，桥的站点本来就监听两种地址族，不需要升级代理。

内核无法把 IPv4 包改写成 IPv6，所以 IPv6 路径由入口上的用户空间转发器承载：它占用端口，为每个用户向出口打开一条连接（UDP 为每个客户端地址一个会话），并原样转发字节。流量仍然两次经过入口，因此入口的流量上限和负载都会计入，入口也不再是“几乎不占用 CPU”：它在搬运字节。UDP 服务器（Hysteria2、AmneziaWG）经 IPv6 路径与经 IPv4 一样工作。这种中转的监听是双栈的，所以旧的“入口域名只保留 A 记录”的建议对它不再适用。

在**反向**方式下，同一设置是这段路径反方向的地址族：出口用它连接入口上的桥站点，可达性检查和它的速度测试也发往该地址。桥是一对节点共用的一个传输，所以地址族按对选择：一条固定 IPv6 的中转会把这对的呼叫改到入口的 IPv6 地址；若同一对里一条固定 IPv4、另一条固定 IPv6，面板会拒绝（`leg_conflict`）。**自动**也会在桥的可达性检查失败时切换，同样每半小时最多一次。

IPv6 同样会被过滤，而且其名单会变化：这正是**自动**的用途。中转行会显示正在使用的地址族（“经 IPv6”），行的链路会显示这段是否通过。

## 使用 MCP

管理员令牌可以读取和管理中转：`relays_list`、`relay_candidates` 和 `relay_check` 用于读取和检测，`relay_plan` / `relay_apply` 用于创建、开启、迁移和删除（始终需要所有者批准）。没有任何工具会显示节点的地址。请参阅 [MCP](../reference/mcp.md)。
