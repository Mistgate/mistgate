## 摘要

- **内存。** 在 1 vCPU / 1 GB 的面板主机上，用户数为 0 到 200 时，Mistgate 面板本身占用 39–44 MiB 私有内存；3x-ui 为 73–76 MiB，PasarGuard 为 273–277 MiB，Remnawave 为 436–464 MiB。Mistgate 仍然最小，但比 10 月（16–20 MiB）多了 23 MiB，对 3x-ui 的优势也从 3.7 倍缩小到 1.8 倍。在同一服务器上运行 VPN 核心和数据库时，前两者的位置对调：Mistgate 为 92 MiB，3x-ui 为 81 MiB，PasarGuard 为 312 MiB，Remnawave 为 815 MiB（10 月为 57、74、297、761）。面板二进制文件从 62 MB 增大到 112 MB。
- **用户变更和重启不会影响隧道。** Hysteria2 隧道运行期间，添加或删除用户、重启面板，Mistgate 和 Remnawave 都没有断开任何连接。3x-ui 在用户变更时会重启 Xray 核心（高负载日中断开 512 个数据流），容器重启时也一样（128 个）；PasarGuard 在面板容器重启时断开了 128 个数据流。
- **这次测量了隧道速度：机器处于空闲状态，并分别测了把核心固定到两个物理核心和不固定两种情况。** 16 和 64 个并行下载时，四个面板在 2 vCPU 的服务器上都达到 5.5–6.1 Gbit/s，Mistgate 领先 3% 至 10%；单个数据流时 Mistgate 为 5.7 Gbit/s，其他面板为 3.7–4.0 Gbit/s。在「高负载日」（64 个数据流，同时每秒有 300 个订阅请求和一次用户变更冲击面板）中，隧道速度保持在：Mistgate 87–89%，3x-ui 65–66%，PasarGuard 53–61%，Remnawave 30–47%。同一面板的三次重复测试在每个吞吐量单元格中相差不超过 10%，因此公布这些数据（参见[隧道：阶段 B 和 D](#隧道阶段-b-和-d)）。
- **Mistgate 的薄弱环节。** 上述内存和磁盘增长。负载隧道中的小请求 p95 比其他面板长 0.6–0.9 ms（1.9–3.3 ms 对 1.1–2.8 ms；10 月的 29 ms 是测试设置的问题，参见[修复之后](#修复之后)）。冷启动时间翻倍（0.33 s 变为 0.66 s；仍是最快的）。通过 API 创建 1000 个用户用了 38 s，是 3x-ui（18 s）的两倍（Remnawave 为 26 s，PasarGuard 为 40 s），主要是受管理 API 速率限制影响（参见单服务器表格下方的说明）。10 月较慢的无缓存订阅路径没有在 v0.2.1 上重新测量。
- **未测量已发布构建的订阅吞吐量**：每个链接每小时最多获取 60 次，因此负载测试只测量了它拒绝请求的速度。
- 测试使用一台桌面计算机上的一个 CPU、一个 WSL2 环境，并重复 3 次：引用任何数据前，请先阅读[这些数据不能说明什么](#这些数据不能说明什么)。

本页所有表格均于 2026 年 11 月 24 日测得，使用各面板的最新稳定版（Mistgate v0.2.1、3x-ui v3.11.0、Remnawave 3.4.11、PasarGuard v5.6.0）；未重新测量的部分已注明，并给出其 10 月的日期。除标注 n=1 的单元格外，数据均为 3 次测试的中位数，括号内为最小值和最大值。所有测试都在一台桌面计算机上的 WSL2 内运行。脚本、compose 文件和汇总结果位于仓库的 [`tools/bench`](https://github.com/Mistgate/mistgate/tree/main/tools/bench) 中。

两种场景：

1. **仅面板**：小型面板主机，1 vCPU 和 1 GB RAM，无交换分区，没有 VPN 流量。测量空闲内存和 CPU、磁盘、启动时间、通过 API 创建 200 个用户，以及订阅负载（50 个客户端，60 s，200 个用户）。
2. **单服务器**：面板、VPN 核心（或节点）和面板数据库全部运行在一台 2 vCPU、2 GB RAM、无交换分区的机器上，1000 个用户，所有面板都使用 Hysteria2。做了两轮：只设置 CPU 配额（阶段 A 至 E），以及把资源组固定到两个物理核心、客户端放在其余核心上（阶段 B 和 D，即 10 月页面的待完成工作）。

## 自 10 月以来的变化

- **版本。** 四个面板都更新了（见上表）。Mistgate 从 v0.1.32 / v0.1.33 升到 v0.2.1。关闭限制的补充构建、性能剖析和清除缓存的测试基于 v0.1.32，**没有**重做；下文对应部分仍是 10 月的数据，并已注明。
- **机器是空闲的。** 10 月系列测试期间，同一台计算机上还有其他工作在运行，隧道吞吐量数据因此被撤回。这一次没有别的任务运行（隧道测试中整台机器只有 22% 至 33% 忙碌，即资源组加客户端），所以公布隧道数据，并附上波动范围。
- **固定核心测试。** 10 月页面的待完成工作已完成：阶段 B 和阶段 D 的隧道部分，资源组固定在两个专用物理核心上（以 WSL 所显示的拓扑为准，参见[这些数据不能说明什么](#这些数据不能说明什么)），客户端和接收端放在其他核心上，重复三次，每 97 ms 探测一次。
- **测试工具。** 新版本迫使我们改了三处：3x-ui 不再使用 `admin/admin`（新数据库会生成随机的首个用户，并只在日志中打印一次，测试工具从日志中读取）；Mistgate 的测试工具会等节点拿到最后一个用户再开始测量（订阅比节点接受全部用户早几秒显示出服务器线路），并且每 5 分钟刷新一次所有者的二次确认（step-up），现在删除用户需要它。测量方法没有变化。
- **变化汇总**（中位数；每对数据中左边是 10 月）：

  **Mistgate 的面板在内存和磁盘上都变大了。** 单独运行时它仍是最小的（39–44 MiB，3x-ui 为 73–76 MiB），但对 3x-ui 的优势从 3.7 倍缩小到 1.8 倍；在单服务器上，3x-ui 现在比它少 11 MiB。二进制文件从 62 MB 增大到 112 MB，主要是因为面板现在链接了 Xray 核心（VLESS 引擎和面板自己的健康检查辅助程序）和 AI 助手的 SDK，v0.1.32 没有这两样；更大的 Web 界面和内置的站点模板又增加了几 MB。空闲时多出的 23 MiB 私有内存只查明了一部分：各软件包的 `init` 函数分配了 7.9 MiB（用 `GODEBUG=inittrace=1` 测得），其余未能归因，这是最先要查的地方。其他三个面板的变化在 3% 至 7% 之间。

表格说明：

- 冷启动指从启动命令到面板主端口首次返回 HTTP 200 的时间。3x-ui 的订阅监听端口（2096）比主端口稍晚才启动；测试工具会在重启后的内存采样前等待它，三次重复测试都有该采样。
- Remnawave 在负载期间触及 1 GB 上限：三次重复测试中，cgroup 记录了 169,000 至 228,000 次 `max` 事件（需要回收内存的分配），均未发生 OOM 终止。其负载期间约 880 MiB 的私有内存是真实占用，而不是缓存。进程组包含 Postgres、Valkey 和三个 Node.js 进程（空闲时 `rw-api`、`rw-processor` 和 `rw-scheduler` 各约 130–146 MiB）。
- 3x-ui 的被测进程组中包含它的 Xray 核心（anon 约 9 MiB）和 fail2ban（约 12 MiB）。如果只比较面板进程，需要将它们扣除：x-ui 本身约 42 MiB，与同一次测量中 Mistgate 面板的 43 MiB 相当。
- PasarGuard 和 Remnawave 的被测进程组中没有运行 VPN 核心（未连接节点）；Mistgate 也没有已连接的节点（为让订阅不为空而需要连接一次的 Agent 在测量前已移除；节点记录保留）。
- Mistgate 在 0 个用户时的 `memory.current` 是页缓存，不是私有内存：第一个窗口中为 224 至 321 MiB，五分钟后 200 个用户的窗口中为 56–58 MiB。内核把安装过程中的文件读取记在了资源组名下（二进制文件现在是 112 MB）；这部分缓存可以回收，不计入 anon。10 月同一单元格为 17–29 MiB，当时二进制文件是 62 MB。10 月的清除缓存测试（每次启动前清除页缓存）没有重做。
- 下面 Mistgate 订阅负载中的 429 数量取决于每链接每小时 60 次的限制，在那里另有说明。该负载下 Remnawave 的 p99 在本轮为 4.1 至 11.7 s（10 月为 1.1 至 3.0 s）；每秒请求数在各次重复测试之间为 132 至 243。

### 订阅负载

50 个并发客户端，60 s，相同的 User-Agent（`v2rayN/7.5.0`），200 个链接，启用 keep-alive。每个面板为每个用户返回一个链接，以 base64 编码的文本正文，长度 152 至 360 字节。各面板链接的类型不同（Mistgate 为 Hysteria2，3x-ui 为 VLESS Reality，Remnawave 和 PasarGuard 为 Shadowsocks），参见末尾说明。

| | Mistgate（已发布版本） | 3x-ui | PasarGuard | Remnawave |
|:--|--:|--:|--:|--:|
| 每秒 200 响应数 | 197（限流器，见下文） | 163 (159-165) | 306 (303-309) | 135 (132-243) |
| p50 / p95 / p99 延迟（ms） | 4.7 / 6.6 / 7.9 | 273 / 470 / 1218 | 151 / 270 / 378 | 90 / 151 / 9478 |
| 非 200 响应 | 99.5% | 0 | 0 | 0（一次重复测试中为 0.01%） |
| 平均 CPU（占一个 vCPU 的百分比） | 98 | 34 | 98 | 97 |

**按设计，已发布版本的 Mistgate 不会承接这种负载。** 每个订阅链接每小时最多可获取 60 次；第 61 次及之后返回 429。每次重复测试中，恰好有 11,799 个请求得到 200（每个链接每小时 60 次，扣除每个链接一次预热请求和负载开始前一次检查请求），另有 250 万至 260 万个得到 429。429 路径开销很小（单 vCPU 上每秒 42,600 至 43,600 次应答，10 月为 27,000 至 34,000 次），因此第一行的「每秒请求数」是拒绝请求的速度，而不是提供服务的速度。它不是测试结果。公共监听端口按客户端地址的令牌桶（每秒 10 个请求，突发 60）没有决定这次测试：在 `--trusted-proxy` 之后，每个链接都通过 `X-Forwarded-For` 使用各自的客户端地址。

3x-ui 在每秒 163 个请求时占用一个 vCPU 的 34%：其瓶颈不是 CPU（10 月时它在每个响应后关闭连接；这次没有再检查）。

### 补充：关闭限制的 Mistgate（修改版构建，10 月，v0.1.32）

**11 月没有重做**：这两个构建需要给 v0.1.32 源码打补丁（diff 在仓库中），而 v0.2.1 没有为使它们可比而做任何改动（diff：[`mistgate-bench-variants.diff`](https://github.com/Mistgate/mistgate/blob/main/tools/bench/mistgate-bench-variants.diff)）。下面的数据是 10 月的，不能说明 v0.2.1 的情况。它们不是已发布构建；切勿将其当作 Mistgate 的结果引用。

| | limits off, render cache on (`nolimit`) | limits off, render cache off (`nolimit-nocache`) |
|:--|--:|--:|
| 更改内容 | 关闭每链接上限和每地址令牌桶 | 同左，并关闭链接的 10 s 渲染缓存 |
| 每秒请求数，状态码 200 | 19,580 (19,331-19,614) | 1,630 (1,612-1,633) |
| p50 / p95 / p99 (ms) | 2.4 / 5.4 / 7.2 | 4.2 / 6.6 / 1,702 |
| 非 200 响应 | 0 | 0 |
| 平均 CPU 占用率 | 100 % | 100 % |

关闭缓存后，每个请求都会读取数据库（包含多个语句，SQLite 会重新解析每条语句）；开启缓存时，每个链接最多每 10 s 读取一次。未缓存路径的性能剖析见[性能剖析](#性能剖析仅-mistgate)。未缓存路径的 1.7 s p99 是少量请求受到饥饿所致（整个测试期间始终约为每秒 25 个请求），并非暂停；将 `GOMAXPROCS=4` 后这一问题消失（p99 为 86 ms，吞吐量相同）。

## 结果：单服务器（2 vCPU，2 GB，无交换分区），Hysteria2，1000 个用户

每个面板在 2 vCPU / 2 GB 资源组内运行的内容：

| 面板 | 资源组内容 |
|:--|:--|
| Mistgate | 面板（原生进程）和 `mistgate-node`（容器） |
| 3x-ui | 一个容器：x-ui、Xray 核心、fail2ban |
| Remnawave | 后端、Postgres、Valkey 和 `remnawave/node`（内含 Xray 核心） |
| PasarGuard | 面板容器和 `pasarguard/node`（内含 Xray 核心） |

每台服务器都使用自签名证书；客户端不验证证书（所有面板相同）。两端均使用 BBR 拥塞控制，不声明带宽，不使用混淆。客户端是 `hyload`，一个基于 Hysteria 2 客户端库（`core/v2` v2.12.3）的小程序；它运行在资源组之外，没有 CPU 限制，位于单独的 cgroup 中，占用 16 个可用 vCPU 中的 140–340% 个 vCPU，而资源组被配额限制在 200%。每个核心容器（Mistgate 节点及其他三个面板的 Xray 核心）的 `GOMAXPROCS` 都等于资源组的 vCPU 数，这也是 Go 运行时在具有相应 vCPU 数的真实服务器上会选择的值；否则容器会按主机的 16 个 CPU 设置 `GOMAXPROCS`（参见[修复之后](#修复之后)）。

阶段：A 为 1000 个用户的空闲状态（60 s 稳定期，120 s 测量窗口）；B 为单个隧道 1、16 和 64 个并行下载（各 30 s），同时每 100 ms 通过同一隧道发送一个小请求；C 为 400 个客户端同时连接，每 2 s 发送一个小请求（60 s）；D 为持续 120 s 的「高负载日」（64 个数据流、来自 1000 个源地址的每秒 300 个订阅请求的风暴，以及每秒通过管理 API 添加一个用户并移除一个用户）；E 为在 60 s、64 个数据流的测试进行到第 20 s 时重启面板（不重启核心）。

于 2026 年 11 月 24 日测得：第一轮只设置 CPU 配额，阶段 A 至 E（下表中的 A、C、E 以及 D 的控制平面各行来自这一轮），第二轮把资源组固定到两个物理核心，阶段 B 和 D，每 97 ms 探测一次。数据为 3 次测试的中位数，括号内为最小值和最大值。「私有内存」指整个资源组的 anon 加内核内存。

| A：memory.current（MiB） | 99 (97-100) | 89 (86-89) | 896 (781-946) | 329 (328-329) |
| A：CPU（占一个 vCPU 的百分比，总额为 200） | 0.21 | 0.55 | 3.53 | 0.29 |

## 性能剖析（仅 Mistgate）

**10 月，v0.1.32 和 v0.1.33；11 月没有重做。** 另行使用 `net/http/pprof` 构建版本做了一轮测试（通过 `go build --overlay` 添加，未修改仓库），收集了 25–30 s 的 CPU 性能剖析，以及 heap/allocs/goroutine/mutex/block 性能剖析和 `GODEBUG=gctrace=1` 数据；测试对象包括空闲面板、订阅高负载（已发布版本，以及关闭限制和缓存的版本），以及单服务器测试中面板和节点的 B64、C、D 阶段。这些测试数据未计入上文。完整分析见 [`results/profiling-summary.txt`](https://github.com/Mistgate/mistgate/blob/main/tools/bench/results/profiling-summary.txt)；未公布原始性能剖析数据。主要发现如下：

- **429 路径的开销已经很低。** 每个被拒绝的请求约消耗 37 µs CPU 时间，其中 49% 用于 socket 系统调用。每个请求分配 3.2 KB 内存，其中 41% 用于标准库解析请求，19% 用于面板自身中间件（`withStart`、`WithClientIP`）生成的两份请求副本，25% 用于响应头映射。拒绝请求期间，anon 内存稳定在 27 MiB（此前为 20 MiB）。每轮测试开始时观察到的 79 MiB 内存来自一次性使用 argon2id 对所有者密码哈希（64 MiB），而非拒绝请求。
- **从缓存渲染订阅消耗 51 µs CPU 时间，不使用缓存则消耗 614 µs**（分配 62 KB 和约 900 个对象）。未缓存路径中，SQLite 为每个请求重新解析和规划相同语句的操作占 CPU 时间的一半（`sqlite3_prepare_v2`，49.8%）；内存分配的 16% 用于对整个 SQL 字符串调用 `strings.ToUpper`，以检查是否以 `SELECT` 开头。
- **未缓存路径的 1.7 s p99 是饥饿所致，并非暂停。** 整个测试期间，每秒约有 25 个请求等待超过 500 ms。设置 `GOMAXPROCS=4` 后，慢请求消失（p99 为 86 ms，吞吐量相同）。读取连接池有 4 个连接，`database/sql` 会将释放的连接交给随机等待者。
- **节点：** 52% 的 CPU 用于 UDP `sendmsg`/`recvmsg`（正在使用 GSO），5% 用于 AES-GCM，19% 用于构建 QUIC 数据包。高频内存分配（37%）和竞争中的互斥锁（`QStream.Write`）位于 `apernet/quic-go` 和 Hysteria 核心中。
- **GC：** 每秒执行 2–6 次回收；资源组独占 CPU 运行时，最长 stop-the-world 时间为 0.26 ms；在单服务器测试中达到配额上限时，则为 46–49 ms。

### 修复之后

本节的表格来自 10 月（v0.1.32 和 v0.1.33，如列标题所示），11 月没有重做；末尾关于隧道的段落除外。

根据上述发现做的三项更改已包含在 v0.1.33 中（下文的第四项也已包含）：

- **存储读取**（`perf(store)`）：每个连接只预处理一次语句并重复使用；读取请求按到达顺序进入 4 连接池；两个连接池始终保持所有连接打开；`SELECT` 检查不再将整个查询转换为大写。
- **公共请求**（`perf(http)`）：使用一个请求上下文，而非创建两份副本；从共享切片读取固定响应头；每次调用不再创建 `strings.NewReplacer`；Mihomo 订阅使用 gzip writer 池。
- **用户变更和密码**（`perf(fleet,auth)`）：每个入站的节点凭据摘要重用一个缓冲区（1000 个用户时，每次变更的内存分配约减少 5 倍；仍需遍历所有用户一次）；同时一次只运行一个 argon2id 哈希，因此并行登录不再各自占用 64 MiB。

剩余的长尾另有原因。为监视可取消的上下文，`database/sql` 会为每个事务和查询启动一个 goroutine，SQLite 驱动则会为每条语句启动一个 goroutine：每次获取订阅约 25 个。在单 CPU 上，这些 goroutine 会使 Go 调度器的本地运行队列溢出到全局队列；忙碌的处理器每 61 轮才会清空一次全局队列，因此 HTTP 读取 goroutine 若进入该队列，其连接最多会等待一秒。第四项更改（`perf(store)`，读取批次使用独立连接且不启动上下文监视 goroutine）移除了这些 goroutine。同一台机器、同一会话、未缓存版本，重复测试 3 次：

| 最慢请求 | 780 ms | 32 ms |

当天机器运行速度更快，因此只比较表格中的两列，不要与上方表格比较。更高的 p50 是服务器满载时 50 个客户端平均分得的处理时间，这些客户端不会暂停（每秒 4,580 个请求时，50 / 4,580 = 10.9 ms）；此前少数客户端的停顿会令服务器对其他客户端空闲。

高负载隧道中的小型请求延迟（阶段 B：三次测试中两次 p95 为 29 ms，另一次为 2.3 ms；1 vCPU 时为 67 ms）最终证实来自测试设置，而非节点。单服务器资源组的配额设置在 systemd slice 上，而拥有独立 cgroup 命名空间的容器无法看到该配额，因此节点的 Go 运行时按主机 CPU 数设置 `GOMAXPROCS`，每 100 ms 周期开始约 80 ms 后便耗尽 2 CPU 配额，随后余下时间都处于停顿状态（运行时跟踪显示，停顿占 19%）。每 100 ms 发送一次探测请求，总会落在周期的同一位置，因此请求要么刚好避开停顿，要么落入停顿，由此产生两种延迟水平。将 `GOMAXPROCS` 设为与资源组 vCPU 数相同后（这也是运行时在真实服务器上选择的值），节点不再停顿。使用相同二进制文件和会话、64 个数据流，并每 97 ms 发送一次探测请求以错开周期：修正前 p95 为 14.7–18.2 ms，修正后为 3.3–3.6 ms，吞吐量从 4.2 Gbit/s 升至 5.4 Gbit/s。现在，`tools/bench` 中的测试工具会为每个核心容器（Mistgate 节点及其他面板的 Xray 核心）设置 `GOMAXPROCS` = vCPU 数。10 月用该测试工具在 v0.1.33 上的复测受到机器上其他负载的干扰（一个面板在 64 个数据流下的吞吐量在各次重复测试之间从 1.5 Gbit/s 波动到 4.2 Gbit/s，慢的几次正是负载生成器只拿到 177–185% 而不是 320% CPU 的那几次），所以当时撤回了隧道各行。11 月在空闲机器上的测试解决了这个问题：阶段 B 中 Mistgate 的小请求 p95 为 1.9–3.3 ms，比其他面板高 0.6–0.9 ms，而不是 29 ms，并且各次重复测试结果一致（参见[隧道：阶段 B 和 D](#隧道阶段-b-和-d)）。

## 方法

### 测试机器

AMD Ryzen 7 7800X3D（8 核、16 线程）、15.5 GB RAM、Windows 11 主机、WSL2（Ubuntu 24.04.4）、Linux 6.6.87.2-microsoft-standard-WSL2、Docker 29.4.1 和 Compose v5.1.3、systemd cgroup 驱动、cgroup v2。11 月的测试于 2026 年 11 月 24 日在没有其他任务运行的计算机上进行：系列测试开始前 Windows 一侧只有 1%–8% 忙碌，同一 WSL 实例中有三个无关的容器处于空闲。每次重复测试开始时的一分钟平均负载（原始 JSON 的 `background` 字段）在仅面板系列中为 0.1–2.2，在单服务器系列中为 2.1–6.0；这是上一次重复测试收尾留下的，不是别的工作，而且每次隧道测试还会记录整台机器的忙碌程度（阶段 B 中为 16 个线程的 22%–33%，即资源组加客户端）。测试工具、二进制文件和面板数据与 10 月一样放在 WSL 的 ext4 磁盘上（结果写到 Windows 磁盘）；9p 挂载会改变启动时间和 SQLite 的表现。负载生成器和接收端也在同一 WSL 实例中运行，位于受限 cgroup 之外。

### 资源限制

- 面板主机：一个 systemd slice `bench-panel.slice`，设置 `CPUQuota=100%`、`MemoryMax=1G`、`MemorySwapMax=0`，并固定到主机的一个 CPU（`AllowedCPUs=15`；在每轮测试前通过 `systemctl set-property` 运行时设置；负载生成器不属于该 slice，也未固定 CPU）。Docker 容器通过 `cgroup_parent: bench-panel.slice` 创建，Mistgate 通过 `systemd-run --slice=bench-panel.slice` 启动，因此每个面板的所有进程（包括 Remnawave 的全部容器）共用同一份配额。每次重复测试前都会停止并重新启动该 slice，使 `memory.peak` 从零开始计数。
- 单服务器：使用 `bench-box.slice`，设置 `CPUQuota=200%`、`MemoryMax=2G`、`MemorySwapMax=0`；最低配置服务器测试则分别设为 100% 和 1G。每个核心容器（Mistgate 节点及其他面板的 Xray 核心）的 `GOMAXPROCS` 均设为 slice 的 vCPU 数，因为容器无法看到 slice 的配额，否则会按主机的 16 个 CPU 设置该值（参见[修复之后](#修复之后)）。
- 仅面板：slice 固定到主机的一个 CPU（`AllowedCPUs=15`，在系列测试前通过 `systemctl set-property` 在运行时设置），与 10 月相同。仅设置配额会允许多线程运行时先在多个主机 CPU 上突发运行，再限流；与之相比，固定 CPU 更接近单 vCPU 服务器的情况。10 月为对照另做了一次不固定 CPU 的重复测试（v0.1.32；没有重做）：

| 仅面板测试，重复 1 次 | 固定 CPU + 配额（10 月的测试） | 仅配额 |
|:--|--:|--:|
| Mistgate：200 个用户时的空闲 anon 内存（MiB）/ 每秒 429 响应数 | 20 / 33,700 | 24 / 15,750 （p99 为 77 ms，之前为 7.4） |
| 3x-ui：每秒 200 个响应时的 p50（ms） | 148 / 296 | 162 / 278 |
| PasarGuard：每秒 200 个响应时的 p50（ms） | 274 / 166 | 102 / 467 |
| Remnawave：每秒 200 个响应时的失败请求数 | 271 / 0 | 251 / 75%（一个 worker 被 1 GB 上限终止，`oom_kill` 为 1） |
| Remnawave：负载期间的 anon 内存（MiB） | 870 | 786 |

  空闲内存、磁盘、启动时间以及 3x-ui 的数据不受 CPU 固定设置影响。PasarGuard 和 Remnawave 的负载数据则会受到影响：仅设置配额时，它们的线程会分布在多个主机 CPU 上运行，并受到配额限制。真实的单 vCPU 虚拟机会呈现与固定 CPU 相似的情况。
- 单服务器：两轮测试。第一轮只设置配额（`CPUQuota=200%`，不固定 CPU），阶段 A 至 E。第二轮把资源组固定到两个物理核心、把客户端固定到其他核心：`AllowedCPUs=0,1,8,9`（线程 0 和 8 是同一个核心，1 和 9 是下一个核心，WSL 中 `lscpu -e` 如此显示）、`CPUQuota=200%`、`GOMAXPROCS=2`，客户端和接收端放在 CPU 2–7 和 10–15 上，阶段 B 和 D，每 97 ms 探测一次，使探测的相位相对 100 ms 的 CFS 周期漂移。WSL 的 CPU 拓扑是虚拟的，参见[这些数据不能说明什么](#这些数据不能说明什么)。

### 测量方式

- 内存和 CPU：每秒采样一次 slice 的 cgroup 文件（`memory.current`、`memory.stat` 中的 anon/file/kernel、`cpu.stat`、`pids`）。空闲数据：内存取 5 分钟空闲期最后 30 s 的平均值，CPU 取整个空闲时间窗口的平均值。峰值取窗口内最大的 1 Hz 采样值，以及 slice 的内核 `memory.peak` 值。
- 磁盘：使用的 Docker 镜像解压后大小总和，或二进制文件大小；数据目录在安装后和创建 200 个用户后的大小。
- 冷启动：从执行启动命令（`docker compose up -d` 或 `systemd-run`）到主端口首次返回 HTTP 200 的时间（Remnawave 使用会读取数据库的 `/api/auth/status`）。
- 用户：通过各面板文档所述的 API 逐个创建（Mistgate 使用所有者会话和 Connect-JSON，3x-ui 使用 `/panel/api/clients/add`，Remnawave 使用 `/api/users`，PasarGuard 使用 `/api/user`）。所有面板均使用相同的虚构用户名 `user1` 至 `user200`（单服务器测试中为 1000 个用户）。
- 负载：使用 `loadgen`（Go 标准库），50 个 worker，轮流请求各链接，先预热一轮，持续 60 s；只统计 200 响应的延迟，其他状态码均计为错误。
- 顺序：仅面板系列轮流测试各面板，每个面板重复三次；单服务器系列在每次重复中打乱顺序（按重复序号作为种子）。每次重复测试前都会清除数据。

### 各面板的设置方式及其与项目文档的差异

- Mistgate：使用项目可复现构建（`release build`）从 v0.2.1 标签构建，未使用发布密钥，因此无法自行更新或安装签名节点包。使用 `serve --listen 127.0.0.1:18080 --trusted-proxy 127.0.0.1 --agent-listen <bridge address>` 启动。由于节点处于活动状态前链接不会包含服务器线路，因此需先让一个节点 Agent 连接一次（在隔离网络中的容器内）；测量前会移除该容器。
- 3x-ui：使用已发布的镜像，而非 compose 文件中的 `build:`；端口绑定到 127.0.0.1；首个面板用户：自 v3.10 起它是随机生成的，并只在容器日志中打印一次（10 月为 `admin/admin`）；一个 VLESS Reality 入站。
- Remnawave：使用官方 compose 文件，并将后端镜像版本从 `:3` 固定为 `3.4.11`（节点 3.4.6）；每个请求都发送 `X-Forwarded-For` 和 `X-Forwarded-Proto: https`（后端会拒绝未经过 TLS 代理的请求）；通过控制面板会话创建 API token（`x-remnawave-client-type: browser`）；使用默认协议配置（一个 Shadowsocks 入站）和默认用户组；一个主机。
- PasarGuard：使用项目默认 compose 文件（主机网络），镜像固定为 v5.6.0（节点 v0.5.7），设置 `UVICORN_HOST=127.0.0.1`；使用默认核心配置（一个 Shadowsocks 入站）；一个主机和一个用户组；使用 `pasarguard-cli generate-temp-key` 生成的临时密钥创建所有者。
- 未调整任何设置。所有面板均未使用 TLS（回环地址上使用普通 HTTP），尽管实际安装时会在前方配置 TLS 代理。

## 引擎基准测试套件

上面的表格比较的是各个面板。这个套件测量节点内部的引擎（Hysteria2、VLESS 和 AmneziaWG），并与它们自己以前的数字对比，这样任何一个变慢的改动在发布前就能被发现。它是回归检查，不是与其他产品的比较。

**测量内容。** 对每个引擎，在由 veth 对连接的两个网络命名空间之间，节点后面的第三个命名空间充当“互联网”：

- 1 条和 8 条并行流的吞吐量（Mbit/s，经隧道下载）；
- 引擎进程在两个阶段传输期间每 GB 使用的 CPU 秒数（来自 `/proc` 的用户加系统时间）；
- 8 条流占满链路时，小请求（64 字节，每 20 毫秒一次）的 p50 和 p99 延迟；
- 引擎进程的峰值常驻内存（`VmHWM`）；
- 每秒握手数：新的 Hysteria2 会话（QUIC 握手加认证）、新的 VLESS REALITY 连接（每个都是一次 REALITY 握手和一个 VLESS 会话，不复用）；AmneziaWG 则是对一个对端重新握手并发一次 ping，节奏受 WireGuard 自身每 20 毫秒一次发起握手的限制，所以最多约 30，主要说明每次都成功。

引擎是本仓库中的真实引擎，按节点启动它们的方式启动：Hysteria2（自签名证书，由客户端固定）、基于 TCP（Vision）和 XHTTP 的 VLESS REALITY，以及用户态后端的 AmneziaWG（使用真实的 amneziawg-go 客户端）。客户端是真实的客户端库（Hysteria 客户端、进程内的 Xray 客户端）。引擎运行在自己的进程里，所以 CPU 和内存都是它自己的。

**网络变体。** `clean`（不做整形）、`rtt50-loss1`（客户端链路每个方向 25 毫秒和 0.5% 丢包：往返 50 毫秒，约 1% 丢包）和 `mtu1280`（客户端链路 MTU 为 1280）。如果某个引擎在某个变体下完全无法传输，就没有对应的用例：Hysteria2 在 1280 字节链路上会被跳过，因为 QUIC 发送带“不分片”标志的 1280 字节数据报，而链路会丢弃它们。

**运行方法。** 需要 Linux、root、`ip`（iproute2）、用于 netem 变体的 `tc`、用于 AmneziaWG 的 `nft` 以及 Go。它会改变网络状态，所以请在 WSL 或一次性机器上运行，绝不要在生产节点上运行。所有命名空间都叫 `mg3-awg-b-*`；主机自己的网卡、路由和 nft 表不会被触碰。

```sh
scripts/bench.sh                                  # 所有引擎和变体；在 Windows 上会自行转入 WSL 以 root 运行
scripts/bench.sh --engines hysteria2,awg --variants clean --seconds 6
scripts/bench.sh --repeat 3 --update              # 用三次运行的中位数生成新的基线
MISTGATE_BENCH=1 go test -tags bench ./internal/node/bench/ -run '^TestBench$' -count=1 -v -timeout 0   # 在 Linux 上以 root 运行，效果相同
```

没有 `MISTGATE_BENCH=1`、没有 root 或没有网络命名空间时，测试会带着提示信息跳过；没有 `tc` 时跳过 netem 变体，没有 `nft` 时跳过 AmneziaWG。报告是 JSON（`bench-report.json` 或 `--out`）：每个 `<引擎>/<变体>` 一个对象。

**基线。** `internal/node/bench/baseline.json` 保存参考运行的数字，以及它所用的内核、CPU 数和 Go 版本。每次运行都会逐项指标与它比较，**任何指标比基线差 15% 以上就会失败**（吞吐量和握手数更低，每 GB 的 CPU、延迟和内存更高）。阈值用 `--threshold`（或 `MISTGATE_BENCH_THRESHOLD`：`15`、`15%` 或 `0.15`）设置。变化小于最小绝对量时，无论百分比多大都不计入（5 Mbit/s、每 GB 0.3 CPU 秒、p50 为 2 毫秒、p99 为 5 毫秒、8 MB、每秒 2 次握手）；没有基线的用例只作记录，基线中有但未运行的用例同样只作记录。绝对数字取决于机器：一台机器上的基线对另一台说明不了什么。请在负责检查的那台机器上，用三次运行的中位数（`--repeat 3 --update`）生成基线；在共享机器上失败时，先当作“在安静的机器上再测一次”，再考虑是否为回归。

**共用端口前端之后。** `vless-tcp-front` 和 `vless-xhttp-front` 是同样的引擎，只是端口由代理的前端共用（见[一个 443，多个服务共用](../guide/shared-port.md)）：引擎从前端的路由而不是自己的套接字接收连接。每一项都与同一次运行中的直连用例比较，使用相同的阈值（默认 15 %，最小变化量也相同），与基线无关；前端一个连接都没有交给引擎的用例会失败。`MISTGATE_BENCH_LOOPBACK=1` 不使用网络命名空间，也不需要 root，在 127.0.0.1 至 127.0.0.3 上运行 `clean` 变体：其数字说明在这台机器上前端与直连用例相比如何，不能与基线的数字比较。

GitHub 工作流 `bench`（**Actions → bench → Run workflow**）在托管 runner 上运行同样的内容。它只能手动启动，绝不在 pull request 或定时任务中运行。

**参考运行**（WSL2，内核 6.6，16 线程，每阶段 4 秒、三次运行的中位数；veth 链路在内存中，因此 clean 的吞吐量远高于任何真实链路，反映的是引擎的 CPU，而不是网络）：

## 这些数据不能说明什么

- 使用一台桌面计算机的一个 CPU、一个 WSL2 虚拟机，重复三次。所有表格的波动都较小（最大的是单服务器上 Remnawave 的空闲内存，700 至 864 MiB，以及它在订阅负载下的 p99），但更换 CPU、内核或文件系统会改变绝对值。11 月机器上没有运行其他任务；10 月有，因此那一轮的隧道数据被撤回。
- **WSL2 的 CPU 拓扑是虚拟的。** `lscpu -e` 显示 16 个线程，其中 n 和 n+8 是同一个核心的两个线程，固定核心的一轮正是据此使用线程 0、1、8 和 9。但客户机的 CPU 由哪些主机线程来运行，是由 Hyper-V 决定的，Windows 也可能迁移它们，所以「两个专用物理核心」指的是客户机看到的两个核心，且客户机的其他任务不在其上运行，并不是对硅片本身的保证。固定核心与仅配额的两轮在阶段 B 以及阶段 D 的排序上一致，说明影响较小，但并不证明它为零。
- 负载由 50 个客户端构成闭环：它反映的是处理请求的开销，而非面板可服务的用户数量。真实客户端每隔数小时获取一次订阅。
- 各面板处理每个请求时执行的操作不同，提供的链接也不同（Hysteria2、VLESS Reality、Shadowsocks）。Remnawave 和 PasarGuard 使用已保存的密码生成 Shadowsocks 线路；3x-ui 生成 VLESS Reality 线路；Mistgate 则生成带固定证书的 Hysteria2 线路。
- Mistgate 使用用户数据的 10 s 缓存响应订阅请求；其他面板没有这样做（或未说明是否这样做）。上方关闭缓存的修改版展示了缓存的影响。
- 使用的数据库不同：Remnawave 需要 PostgreSQL，其他面板使用 SQLite。PasarGuard 还支持 PostgreSQL 和 MySQL；本次只测量了其默认设置。
- 测量 Mistgate 时，节点记录仍在，但 Agent 已移除；其他面板没有节点。单服务器测试则包含 VPN 核心。
- 页缓存在各面板之间、各窗口之间的计入并不均匀：10 月 Mistgate 的二进制文件由另一个 cgroup 复制，其文件缓存很小；11 月安装后的第一个窗口里它有 224–321 MiB（112 MB 的二进制文件和安装时读取的文件），而其他面板则在资源组内读取文件。因此本文以 anon 为主要数据。10 月清除页缓存的测试（每次启动前清除）没有重做。
- 未测量内容：除类似环回连接中的 Hysteria2 外的 VPN 数据平面速度（接收端和客户端位于同一台机器，没有网络传输）、其他协议、管理 Web 界面、Telegram 机器人、升级和备份、多节点、高延迟或有丢包的路径、面板前方的 TLS 代理，以及超过一周的运行情况。
