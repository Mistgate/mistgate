The panel has a built-in Model Context Protocol (MCP) server, so an AI agent can read the fleet and make day-to-day changes. It uses the same API tokens and the same procedures as the [admin API](api.md): the token's profile decides what the agent sees and may do, and every call is in the audit log. Nothing changes in one call: an agent plans a change, then applies it, and the riskiest changes wait for the owner's approval in the admin.

The HTTP endpoint below is available in the VPS edition. The Edge edition does not serve `/mcp` in phase 1; Edge support is planned for phase 2 behind a separate Worker service binding.

## The endpoint

```text
<admin URL>mcp
https://panel.example.com/<prefix>/mcp
```

- Streamable HTTP, stateless, JSON responses. It offers tools only: no resources, prompts or sampling.
- It exists only on the admin surface (the secret prefix, host or listener), never on the public side.
- Every request needs `Authorization: Bearer tk1_…` and is checked again: a revoked or expired token stops at its next request. There is no session to take over.
- `tools/list` shows only the tools the token's profile may use.

**AI → MCP and tokens** shows the address and a ready snippet for each kind of client.

## Connect a client

Create a token in **AI → MCP and tokens** with the narrowest profile that works (see [Token profiles](api.md)). Then:

**Claude Code** (Streamable HTTP):

```sh
claude mcp add --transport http mistgate https://panel.example.com/<prefix>/mcp --header "Authorization: Bearer <token>"
```

**Any client that speaks Streamable HTTP**:

```json
{
  "mcpServers": {
    "mistgate": {
      "type": "http",
      "url": "https://panel.example.com/<prefix>/mcp",
      "headers": {
        "Authorization": "Bearer <token>"
      }
    }
  }
}
```

**Clients that can only start a command** (for example Claude Desktop) use the stdio proxy, `mistgate mcp`, on your own computer. Save the token as the first line of a file only you can read, then:

```json
{
  "mcpServers": {
    "mistgate": {
      "command": "mistgate",
      "args": ["mcp", "--url", "https://panel.example.com/<prefix>/", "--token-file", "<path-to-token-file>"]
    }
  }
}
```

### The stdio proxy

`mistgate mcp --url <admin URL> --token-file <file>` runs a local MCP server on stdin and stdout and forwards every message to the panel's endpoint. It decides nothing, caches nothing and knows no tool: the panel answers.

- The token is read only from the file's first line, never from the command line or the environment, and never printed. A warning is printed when others can read the file (not checked on Windows).
- `--url` must be `https`, except for `localhost` or a loopback address. Redirects are not followed, so the token goes nowhere else.
- When the panel refuses the token (expired, revoked or the wrong profile) the proxy stops with that message.
- `--url` and `--token-file` fall back to `MISTGATE_URL` and `MISTGATE_TOKEN_FILE`.

`mistgate` builds for Linux, macOS and Windows: `go build ./cmd/mistgate` makes the binary for the computer the agent runs on. See [CLI](cli.md).

## Limits

| Limit | Value |
|---|---|
| Tool calls at a time, per token | 4 (more: 429 "at most 4 tool calls at a time per token") |
| Requests per minute | the token's own limit |
| Request body | 3 MiB |
| A tool result | 32 KiB; long lists are halved until they fit and marked as truncated |
| Time per call | 30 s for reads and plans, 90 s for an apply |
| Open plans | 20 per token; 50 waiting for the owner across the panel |
| Stored arguments of a plan | 8 KiB (3 MiB for a decoy bundle upload) |

## Tools

### Read tools

Read tools change nothing. Arguments are ids and plain words, never URLs: no tool fetches anything an agent names. A node can be given by its id or its exact name. The Profile column is the lowest profile that sees the tool; higher profiles see it too.

With Globalping on, `probes` lists the networks asked, each with `eyeball` (a home or mobile probe) and, in a `partial` round, `dark` (it got nothing from this node but reached another); `no_probe` names the operators that had no home or mobile probe online in that round. | `update_download_timeout` | Admin | `timeout_seconds` (300 to 7200 seconds; applies to newly sent updates, while a step already in progress keeps its captured window) | always |
| `log_level` | Admin | `level` (`debug`, `info`, `warn` or `error`). Sets the panel's log level until its next restart, when it returns to `--log-level` / `MISTGATE_LOG_LEVEL`. Removes nothing. | no |
| `node_debug_capture` | Admin | `node`, `level` (`debug` or `info`, default `debug`), `sources` (at most 8 log sources such as `agent`, `hysteria2`, `xray`, `awg`, `kernel`; none = all), `duration_s` (1 to 900, default 300). The node must be online and its agent must list `debug/1`; one capture per node at a time. The node raises its log level for the sources, keeps up to 20000 records (4 MiB) and ships them cleaned when the time is up; it puts the level back by itself. Read the result with `node_debug_logs`. Audit-logged with who asked, the node, the sources and the duration. The `kernel` source reads the node's kernel log from 30 minutes before capture start through the end; firewall packet-log lines are counted but not kept. On a kernel-backend node, choosing `awg` turns on the module's debug output during the capture and adds a summary of handshake initiations without a response within five seconds. `kernel` requires an agent with `debug/2`; other sources continue to work with `debug/1`. | no |
| `retention` | Admin | `values`: setting name to its new value (names, units and limits from `retention_status`). A shorter time deletes the older rows at the next hourly sweep, for good. | always (step-up) |
| `task_create` | Admin | Plan: `name`, `kind` (`check` or `assistant`), `schedule` (`every 15m`, `every 2h`, `daily 07:30`, `weekly mon 07:30`, in the panel's time zone; a check at most every 5 minutes, an assistant task every 15), for a check `steps` (1 to 8: `tool`, `args`, `conditions` of `path`, `op` and `value`, `error_is_problem`), for an assistant task `prompt` (up to 4000 characters), `notify_telegram`, `disabled`; apply: `confirm_token` only. The plan checks the definition by the panel's own rules: the tools a check may run (the operator profile's reads and probes, no plan, apply or task tool), their arguments against each tool's schema, the conditions, the minimum interval, and no secret in a name, an argument or a prompt (`secret_in_task`). At most 50 tasks. The task belongs to the owner and its runs act with the operator profile. | always |
| `task_update` | Admin | Plan: `task_id` and only the fields to change (`name`, `schedule`, `steps` replace all the old ones, `prompt`, `notify_telegram`, `enabled`); the kind stays. A changed task starts with a clean state: its open alerts close. If the task changes in the panel before the apply, the apply fails with `changed_since_plan`. | always |
| `task_delete` | Admin | Plan: `task_id`. The task and its runs go, its open alerts close; an assistant task's conversation stays with the owner. | always |
| `rollout_pause`, `rollout_resume`, `rollout_cancel` | Admin | `rollout_id` from `updates_status` | always |
| `node_rollback` | Admin | `node` | always |
| `node_install` | Admin | Plan: `host`, `port` (default 22), `username` (root or a user with passwordless sudo), node `name` (2 to 24 letters, digits or hyphens), `address`, optional `country_code`, `location`, `provider`; apply: `confirm_token` only. The plan reads only the server's public host key. The owner confirms the host key and chooses the panel key or enters the SSH password on the approval screen; a password install also adds the panel key by default | always |
| `node_server_password_rotate` | Admin | Plan: `node` id or the exact name of a live node (a retired node is refused); apply: `confirm_token` only. The panel generates the new password itself and never returns it; the owner can reveal it on the node's **Server** tab | always |
| `node_server_key_add` | Admin | Plan: `node` and either one public `public_key` line or `panel_key: true`; apply: `confirm_token` only. The owner approves the key type, fingerprint and untrusted comment before it is added. Private keys are never accepted. | always |
| `node_server_key_remove` | Admin | Plan: `node` and `key`, a `key_id` from `node_server_keys_list` (or a whole SHA256 fingerprint); apply: `confirm_token` only. Removing the panel key is allowed only after the panel proves the saved password works. | always |

`relay_apply` keeps the panel's own order for `create` and `enable`: it makes the relay (switched off), checks the leg, switches it on, and the panel then checks the path from outside. A relay that fails a check stays switched off and the apply fails with the stage (`leg` or `path`) and its code; moving the port of a relay that is on checks the path again and switches the relay off if it fails. The second server leaves or reaches subscriptions at their next refresh. See [Relays](../guide/relays.md).

Every `_plan` also takes `reason`: the agent's own words, at most 300 characters, shown to the owner as a quote. No tool takes or returns a server password: the owner chooses the panel key or types the install password on the approval screen, and the panel generates rotated passwords itself. `user_create` never returns the new user's subscription link: the owner copies it in the admin.

`os_rollout_start_plan` does one node at a time, with the owner's approval: nothing is installed or rebooted before the owner approves it in the admin. People on the node are disconnected while it reboots (about two minutes). The tool has no way to override the node's own checks. There is no tool yet for several nodes, for a time window, for refreshing the package lists or for the panel's own server.

`rollout_start_plan` updates one selected node now; it cannot start a fleet-wide update. It takes only a node whose agent can update itself and is older than the bundle (outdated, failed or rolled back), and it is refused while another rollout is running or paused. The plan is pinned to the signed bundle trusted when it was made: if the bundle changes before it is applied, the apply fails and a new plan is needed. `node_update_schedule_plan` saves a future update for one node after owner approval; the node may be offline when it is planned, and a new schedule replaces the node's previous one. The saved task is pinned to that signed release and fixed UTC offset. If the node is offline when due, the panel waits up to two hours for it to reconnect, then marks the task missed and never starts it by itself; if the signed bundle changes, the panel keeps the task visible and does not substitute a different release. Use `node_update_schedule_cancel_plan` to cancel a pending task. Changing `update_timezone` affects new schedules only; existing tasks keep their saved instant and offset. `update_download_timeout` changes the download window for newly sent updates; compatible agents receive it with the command, older agents keep their built-in limit, and an update already in progress keeps the window captured when it was sent.

`subscription_app_upsert` and `subscription_app_remove` change one app of the page every user sees, found by its platform and its name ignoring case (a name two apps of one platform share is refused: change those in the admin). A new app goes to the end of the list. The values are checked exactly like a save in **Subscriptions → User page**: an http(s) download link, an add-link template that starts with an app's own scheme (`happ://add/{url}`, `myclient://add?url={url_enc}&name={name_enc}`) or http(s) but never `javascript:`, `data:` and the like, the known placeholders only, at most 30 apps; on top of that the agent's text may not contain invisible formatting characters. The plan reads the whole settings and remembers their state; if anyone saves the subscription settings before the apply, the apply fails with "the subscription settings changed after the plan" and nothing is overwritten: make a new plan. In `subscription_settings_get` and in the agent's copy of a plan, link query strings and long path segments read `[redacted]`, like every result; the owner's approval card shows every value in full.

The Telegram proxy is one of the three switches in `apps` of `user_create` and `user_update`. A field you leave out keeps the user's value, so `{"apps": {"telegram": true}}` changes Telegram alone. Switching it on makes the person's Telegram key and switching it off revokes it; the plan names the Telegram proxy among the apps. At least one of `happ` and `amnezia` must stay on: Telegram comes in addition. There is no tool for the key itself, and none returns the `tg://proxy` links: re-issuing or revoking a key, and reading the links, are done by the owner in the admin ([MTProto](../guide/mtproto.md)).

The Mistgate app is a fourth field of `apps` (`mistgate`, on by default). It works only while `happ` is on. The plan words it as a fact of its own, `app_mistgate`, and it needs the same approval as any other change of a user. `client_api_settings` also reads how many people have the app on and how many devices are connected with a key (`people`, `people_on`, `devices`).

## Plan and apply

Some temporary refusals before any work starts leave a plan in `planned` or `approved` until its original expiry; the response says `busy`, gives a reason code and tells you when to retry with the same `confirm_token`. The expiry is not extended, successful applies cannot be repeated, and other failures still mark the plan `failed`.

1. The agent calls `<tool>_plan` with the arguments. The panel validates them, reads what it needs and describes the change in its own words. Nothing changes. The result:

   ```json
   {
     "plan_id": "pln_...",
     "summary": "Disable 5 users: their connections end and their devices are dropped from the nodes.",
     "facts": [{"key": "count", "value": "5"}, {"key": "users", "value": "...", "untrusted": true}],
     "needs_approval": true,
     "danger": ["bulk"],
     "expires_in_s": 600,
     "confirm_token": "cf_...",
     "next": "..."
   }
   ```

2. The agent shows the plan to the person it works for and waits for their go-ahead. If `needs_approval` is true, it also waits for the owner.
3. The agent calls `<tool>_apply` with the `confirm_token`, its only argument. The panel runs exactly the stored arguments, once, and answers with `plan_id`, `status: "applied"` and a one-line result.

The confirm token:

- works once, for 10 minutes, and only for the token that made the plan and only with that tool;
- carries no arguments: they cannot change between plan and apply;
- applying a plan that was already applied returns the same result again; a token of another plan, tool or API token is simply "unknown confirm token".

When an apply cannot run, it says why: "waiting for the owner to approve plan pln_…; it expires at …", "rejected by the owner", "expired: make a new plan", "already running", "failed: …. Make a new plan.", "the token was revoked", or "timeout, outcome unknown: check before retrying".

### Which plans wait for the owner

A plan needs the owner when one of these applies (the `danger` list):

| Code | Meaning | Tools |
|---|---|---|
| `step_up` | The operation itself asks for a fresh confirmation in the admin. | the rollout tools, `os_rollout_start`, `os_rollout_cancel`, `node_rollback`, `node_update_schedule` and its cancel, `update_timezone`, `update_download_timeout`, `retention`, `node_install`, `node_server_password_rotate`, `node_server_key_add`, `node_server_key_remove` |
| `fleet` | It changes what runs on the nodes or removes access from users. | `node_fix`, `node_decoy`, `node_ipv6`, `relay`, `group_update`, the rollout tools, `os_rollout_start`, `os_rollout_cancel`, `node_rollback`, `node_update_schedule` and its cancel, `node_install`, `node_server_password_rotate`, `node_server_key_add`, `node_server_key_remove`; all profile creation, update and deployment plans |
| `bulk` | It touches more than 3 users at once. | `user_disable`, `user_reset_traffic` |
| `user_change_limit` | With this plan the token would pass its hourly limit of user changes (10, see [Limits](api.md#limits)), so the plan waits for the owner instead of being refused. The card shows how much of the limit is used. | `user_disable`, `user_reset_traffic`, `user_update`, `device_revoke` |
| `traffic` | It sends bulk test traffic between nodes. | `path_speed` |
| `user_page` | It changes a shared subscription setting or data users see or receive. | `subscription_app_upsert`, `subscription_app_remove`, `subscription_rules_set`, `subscription_texts_set`, `subscription_link_limits_set`, `subscription_page_set`, `dns_settings_set`, `dns_preset_create`, `dns_preset_update`, `dns_preset_delete`, `node_update` |
| `schedule` | It makes the panel run tools or the assistant on its own, again and again. | `task_create`, `task_update`, `task_delete` |

`group_update` uses `fleet` because changing a group's profiles or disabled nodes can change its members' access. `group_delete` refuses while people are in the group. `node_update` is limited to metadata and subscription-facing switches; all its changes use owner approval because the underlying node update API also accepts runtime-changing fields, which this tool does not expose.

Profile plans validate settings and node additions before storing a plan. Every profile change waits for owner approval in the admin. `profile_update` and `profile_deploy` use the profile version read by the plan; if it changes before apply, apply fails with `changed_since_plan`. Deployment merges group links with their current state at each step and reports completed steps if a later step fails. A failed `profile_create` rolls back the new profile and inbounds; deleting the profile also removes its group links. Secret values never appear in profile reads, plan facts, stored plan arguments or audit entries.

### Where the owner approves

Such a plan appears in **AI → Waiting for you**, with a badge in the admin; if the owner linked Telegram, the panel also sends a message that a plan waits, with a link there (the decision is made in the admin only: see [Telegram alerts](../operations/telegram-alerts.md)). The owner sees the change in the panel's own words, the danger notes, the agent's reason (marked "Written by the agent. The panel did not check it.") and the time left, then chooses:

- **Approve**: asks for the owner's passkey or authenticator code once more. The agent's apply goes through after this, for this plan only.
- **Reject**: the agent's apply fails with "rejected by the owner".

For `node_install`, the approval card shows the SHA-256 host key fingerprint the panel read and its key type (the agent's copy of the plan has the fingerprint redacted, like any key-shaped value). The owner compares it with a trusted copy, ticks the confirmation and chooses how the panel logs in: **Panel key** (the card shows the panel's public key, which must already be on the server; the choice appears when the plan names the panel key) or **Password** (the owner types the server's SSH password there; the install then also adds the panel key to the server by default, so the panel logs in by key from then on). **Approve** stays disabled until the host key is confirmed and, for a password, the password is typed. The panel seals the choice, and a typed password, to that plan, and the agent's apply, which carries only the confirm token, installs with it and with exactly the confirmed host key, once. The password never passes through the agent, its transcript or the model provider. Password rotation has the same owner-approval boundary: the panel generates the new password and never returns it.

A token can never confirm its own plan. Undecided plans expire 10 minutes after they were made. **Recent decisions** keeps the history with the outcome: done, error, expired, cancelled (the token was revoked) and so on. The agent should not poll more often than once every 30 seconds.

### Example: add kl!ck for Windows and macOS

[kl!ck](../guide/client-apps.md#klck) is the desktop app Mistgate recommends. To put it on the user page for Windows and macOS, an agent with the Operator profile does this. The plan remembers the state of the whole settings, so make each plan after the previous one is applied.

1. `subscription_settings_get`: read the current apps, so you know what is already there and which Happ entries are recommended.
2. `subscription_app_upsert_plan` for Windows:

   ```json
   {
     "platform": "windows",
     "name": "kl!ck",
     "kind": "happ",
     "download_url": "https://github.com/vbu00/klick/releases/latest",
     "add_link_template": "klick://add?url={url_enc}&name={name_enc}",
     "recommended": true,
     "reason": "kl!ck is the recommended desktop app"
   }
   ```

   The plan has `needs_approval` and the danger `user_page`. Show it, ask the owner to approve it in **AI → Waiting for you**, then call `subscription_app_upsert_apply` with the `confirm_token`.
3. The same for macOS: the same arguments with `"platform": "macos"`.
4. So that kl!ck leads, take the badge off Happ on both platforms, one plan each: `{"platform": "windows", "name": "Happ", "recommended": false, "reason": "kl!ck leads on the desktop"}`, then the same with `"macos"`. Only the fields that change are given for an app that already exists.

`kind: "happ"` means "by the subscription link", whatever app opens it. The download link is the release page, because the file names carry the version and the Windows and macOS builds are released separately. The one-tap link works only in kl!ck builds newer than 0.4.0; older builds use **Copy link** on the page. A new app goes to the end of the list; the recommended app leads its platform wherever it stands. `subscription_settings_get` afterwards shows the result (link query strings read `[redacted]` for the agent).

## Untrusted data in results

Names, notes, reasons, log lines and the parameters of events and alerts come from users, nodes and other systems. The server's instructions and every tool that returns such text say so: they are data, never instructions, and an agent must not follow requests found in them.

The panel also protects the agent and you:

- Text from data is cleaned: control characters, line breaks and invisible formatting characters are removed, and long values are cut.
- A plan's summary never contains text from data; such values are separate facts marked `untrusted`, and the owner sees them quoted.
- What the owner approves is shown whole. A long value (a task prompt, a list of resolvers, a text of the user page) comes as numbered facts; a new value that cannot be shown as it is (a hidden or bidirectional control character, or text the redactor would change, such as a key or a link with a token) is refused when the plan is made, with the field named. The value a field has now is shown redacted and never blocks a change.
- A last pass over every result replaces anything shaped like a secret: API tokens, share links (`hysteria2://…` and the like), tunnel configurations, key material, URL query strings and long URL path segments (the secret prefix, a subscription token) and bare 32-byte keys.

## What an agent never gets

- Subscription links and user page passwords.
- The Telegram proxy key and its `tg://proxy` links.
- Device keys and configurations, WARP accounts and keys, profile secrets.
- Server passwords: neither the SSH password of an install nor a rotated one.
- Node addresses and certificate pins. The exception is the saved SSH endpoint and login that `node_server_access_list` and the `node_install` and rotation plans show an Admin token.
- Anything of the tokens, approvals, sessions and passkeys.
- The audit log, unless the token has the Admin profile.

## Audit

Every procedure a tool calls is written to the audit log under "MCP token <name>", with the source MCP. Plans and applies add their own rows: "planned a change: <tool>" and "ran the planned change: <tool>"; the owner's decisions appear as "approved the change" or "rejected the change". **Settings → Audit** filters them by the source MCP.
