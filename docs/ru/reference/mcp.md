В панель встроен сервер Model Context Protocol (MCP), чтобы ИИ-агент мог смотреть на флот и делать повседневные изменения. Он использует те же API-токены и те же процедуры, что и [API админки](api.md): что агент видит и может, решает профиль токена, а каждый вызов попадает в журнал аудита. За один вызов ничего не меняется: агент сначала планирует изменение, затем применяет его, а самые рискованные изменения ждут одобрения владельца в админке.

Описанный ниже HTTP-эндпоинт доступен в VPS-редакции. В edge-варианте `/mcp` на этапе 1 не обслуживается; поддержку Edge планируют добавить на этапе 2 через service binding к отдельному Worker.

## Адрес

```text
<адрес админки>mcp
https://panel.example.com/<prefix>/mcp
```

- Streamable HTTP, без состояния, ответы в JSON. Только инструменты: ни ресурсов, ни промптов, ни sampling.
- Адрес есть только на стороне админки (секретный префикс, хост или отдельный адрес) и никогда — на публичной стороне.
- Каждому запросу нужен `Authorization: Bearer tk1_…`, и каждый проверяется заново: отозванный или истёкший токен останавливается на следующем же запросе. Сессии, которую можно перехватить, нет.
- `tools/list` показывает только инструменты, разрешённые профилю токена.

**ИИ → MCP и токены** показывает адрес и готовый фрагмент настройки для каждого вида клиента.

## Подключение клиента

Создайте токен в **ИИ → MCP и токены** с самым узким профилем, которого хватает (см. [профили токенов](api.md)). Затем:

**Claude Code** (Streamable HTTP):

```sh
claude mcp add --transport http mistgate https://panel.example.com/<prefix>/mcp --header "Authorization: Bearer <token>"
```

**Любой клиент со Streamable HTTP**:

```json
{
  "mcpServers": {
    "mistgate": {
      "type": "http",
      "url": "https://panel.example.com/<prefix>/mcp",
      "headers": {
        "Authorization": "Bearer <token>"
      }
    }
  }
}
```

**Клиенты, которые умеют только запускать команду** (например, Claude Desktop), используют stdio-прокси `mistgate mcp` на вашем компьютере. Сохраните токен первой строкой файла, который читаете только вы, затем:

```json
{
  "mcpServers": {
    "mistgate": {
      "command": "mistgate",
      "args": ["mcp", "--url", "https://panel.example.com/<prefix>/", "--token-file", "<path-to-token-file>"]
    }
  }
}
```

### stdio-прокси

`mistgate mcp --url <адрес админки> --token-file <файл>` запускает локальный MCP-сервер на stdin и stdout и пересылает каждое сообщение в панель. Сам он ничего не решает, ничего не кеширует и не знает ни одного инструмента: отвечает панель.

- Токен читается только из первой строки файла, никогда из командной строки или окружения, и никогда не печатается. Если файл читают другие, печатается предупреждение (в Windows это не проверяется).
- `--url` должен быть `https`, кроме `localhost` и loopback-адресов. Перенаправления не выполняются, так что токен никуда больше не уйдёт.
- Когда панель отклоняет токен (истёк, отозван или не тот профиль), прокси останавливается с этим сообщением.
- Запасные переменные для `--url` и `--token-file` — `MISTGATE_URL` и `MISTGATE_TOKEN_FILE`.

`mistgate` собирается под Linux, macOS и Windows: `go build ./cmd/mistgate` соберёт бинарник для компьютера, на котором работает агент. См. [CLI](cli.md).

## Ограничения

| Ограничение | Значение |
|---|---|
| Одновременных вызовов инструментов на токен | 4 (больше — 429 «at most 4 tool calls at a time per token») |
| Запросов в минуту | собственный лимит токена |
| Тело запроса | 3 МиБ |
| Результат инструмента | 32 КиБ; длинные списки уменьшаются вдвое, пока не поместятся, и помечаются как урезанные |
| Время на вызов | 30 секунд на чтение и план, 90 секунд на применение |
| Открытых планов | 20 на токен; 50 ожидающих владельца на всю панель |
| Сохранённые аргументы плана | 8 КиБ (3 МиБ для загрузки сайта-ширмы) |

## Инструменты

### Инструменты чтения

Инструменты чтения ничего не меняют. Аргументы — идентификаторы и простые слова, никогда не URL: ни один инструмент не загружает то, что назвал агент. Ноду можно указать идентификатором или точным именем. Столбец «Профиль» — самый младший профиль, который видит инструмент; старшие профили видят его тоже.

| Инструмент | Профиль | Что возвращает |
|---|---|---|
| `fleet_status` | Только чтение | Все ноды со статусом, причиной, людьми онлайн, скоростью и CPU; итоги, число алертов и главных потребителей сейчас. |
| `fleet_digest` | Только чтение | Проблемы флота одним вызовом: `hours` (от 1 до 72, по умолчанию 24); всё считается только внутри этого окна. В `problem_nodes` у каждой ноды список причин (`code`, `count`, `last_at`): простои и всплески с длительностью (`minutes` и `minutes_in_window`, обрезанные по окну), алерты, открытые в окне или всё ещё открытые, по видам, предупреждения и ошибки журнала по источникам, проваленные раунды проверок, `path_lossy` и другие предупреждения, смены вердикта по стране, сбои и откаты обновлений и то, что нода сейчас не в сети. `quiet_nodes` перечисляет остальные. В `totals` итоги флота; `traffic_hourly` и `online_hourly` — почасовые ряды, которых нет в `fleet_status`, а у проблемных нод есть `spark_bytes_24h`. История проверок почасовая, поэтому считаются корзины, пересекающие окно. `unavailable` называет часть, которую не удалось прочитать. |
| `user_diagnose` | Только чтение | Почему человек не может подключиться, одним вызовом: `user_id` и необязательный `hours` (от 1 до 168, по умолчанию 24). Пользователь и его доступ (статус, срок, квота, лимит и список устройств), ноды и профили, которые даёт его подписка (только структура, как в `subscription_preview`), по устройству и ноде вердикт соединений по счётчикам (`ok`, `rejected`, `unanswered`, `answers_lost`, `stalled`, `throttled`, `frozen`, `lossy`, `slow`, `no_attempts`) с `signals`, алерты и события о человеке, состояние его нод (статус, вердикт по стране, сбои проверок) и короткий машиночитаемый список `findings` (`device_limit_reached`, `expired`, `disabled`, `over_quota`, `never_connected`, `no_attempts_in_window`, `rejects_auth`, `handshake_unanswered` (AmneziaWG: нода не отвечает, наша сторона), `handshake_answers_lost` (нода отвечает, а ответы не доходят: обратный путь перерезан), `stalls`, `tcp_freeze_16k` (соединения VLESS встают после первых 8–32 КиБ: TCP-троттлинг), `freezes`, `high_loss`, `high_rtt`, `node_down`, `node_blocked_in_country`, `no_node_access`, `no_profiles`, `device_blocked`, `no_counters`) с `severity`, ссылками `evidence` и `detail`; `verdict` — самая серьёзная находка. С агентами `links/3` у соединения есть ещё `tcp_stalls`, `tcp_stalls_16k`, `initiations`, `responses` и `responses_unmatched`, а `not_known` называет те из них, которые нода сказать не может (старый агент, бэкенд AWG в ядре). Только числа: ни ключей, ни ссылок, ни пароля страницы, ни адресов клиентов. |
| `timeline` | Только чтение | Что произошло, сначала новое, одним нормализованным списком `{at, kind, severity, code, node, subject, summary_key, params, ref}` из событий, моментов открытия и закрытия алертов, журнала нод (одна запись на ноду, источник и час), перезапусков агента (`restart`), раскаток и, только для профиля admin, журнала аудита (без адресов). `node` или `user` сужают выборку; окно задают `hours` (от 1 до 168, по умолчанию 24) или `from` и `to` (unix-секунды); фильтры — `kinds`, `min_severity` и `changes_only` (аудит, раскатки, события `state_applied`, профилей, ретрансляторов, настроек и обновлений). `limit` (по умолчанию 50, не больше 100) и `next_cursor` обходят все источники в одном порядке. `partial_sources` называет источник, упёршийся в предел чтения. |
| `node_get` | Только чтение | Одна нода: статус и причина, данные хоста, входящие подключения с состоянием, `direct_in_subscriptions` (попадает ли адрес ноды в подписку) и `cdn` (подключаются ли клиенты через CDN-хост), до 10 людей онлайн, заметки владельца и `ipv6`: включён ли его [вход по IPv6](../guide/nodes.md#вход-по-ipv6), может ли нода его принять (`unavailable_reason`: `no_ipv6`, `ipv6_broken`, `agent_old`, `not_checked` или `main_is_ipv6`) и последняя проверка адреса. Без адресов, ключей и отпечатков сертификатов. |
| `nodes_get` | Только чтение | `node_get` для многих узлов одним вызовом: `nodes` — список id или точных имён узлов, пусто = каждый узел, кроме выведенных (не больше 50). Если ответ слишком велик, сначала уходят пользователи онлайн, затем целые узлы, и ставится `truncated`. |
| `warp_status` | Только чтение | Есть ли у ноды WARP-аккаунт и включён он или на паузе; состояние агента, colo, возраст рукопожатия, статус и задержка проверок Cloudflare и другого сайта, время регистрации, наличие токена для обновления аккаунта и профили с выходом через WARP. Без адресов, ключей, идентификатора аккаунта, лицензии и токенов. Без `node`: такая же краткая строка для каждого узла, кроме выведенных (`unavailable` называет узлы, которые не ответили). |
| `relays_list` | Только чтение | [Ретрансляции](../guide/relays.md): порты на ноде входа, которые пересылают сервер ноды выхода как есть. Необязательный `node` оставляет те, где она на любом конце. По каждой: ноды входа и выхода, сервер выхода (профиль, протокол, сеть), порт на входе и на выходе, `enabled`, `state` (`pending`, `active`, `failed`; `last_error_code` — первое слово ошибки агента), `exit_live`, `agent_supported` и `last_check`: плечо (вход достаёт до сервера выхода) и путь (третья нода достаёт до него через вход), каждое — `ok`, `fail` или `skipped` с кодом, нодой, отправившей пробу, и для UDP числом отправленных и посчитанных пакетов. Сохранённые данные, ноды не опрашиваются. Без адресов. |
| `relay_candidates` | Только чтение | Для ноды входа (`node`): серверы других нод, которые она могла бы ретранслировать. По каждому: `inbound_id` (его принимает `relay_plan`), нода выхода, профиль, протокол, сеть и порт; `unsupported` (`cdn`, `acme_ip`, `awg`, `build_failed`; пусто — можно ретранслировать); `hop` (у сервера диапазон hop, ретрансляция передаёт один порт); `relay_id` (этот вход уже его ретранслирует); `exit_country_check` (как страновая проверка видит выход: `ok`, `partial`, `blocked`, `listed` или `no_data`, и сети, где он недоступен); `entry_reaches_exit` (`reach`, `partial`, `blocked` или `no_data`; известно, если ТСПУ-зонд работал с этого входа). `entry_country_check` — то же про сам вход. `no_data` значит «неизвестно», а не «всё хорошо». Без адресов. |
| `node_metrics` | Только чтение | Текущие CPU, RAM, диск и сеть ноды, трафик за сегодня, люди онлайн по протоколам, главные пользователи за сегодня. С `hours` (1–720) также нагрузка хоста по часам (CPU среднее и пик, softirq, RAM, сеть, сессии; окна длиннее 96 часов группируются в точки по `bucket_hours`) и пики всего окна с их часом. Панель хранит её 90 дней. От агента, который их сообщает, `resources` добавляет steal и ожидание ввода-вывода, своп, таблицу соединений (число, лимит, заполнение), сокеты TCP и UDP, скорость линка сетевой карты и сам процесс агента (CPU, память, горутины, потоки, открытые файлы против лимита); без него агент слишком старый, чтобы это сообщить. Без `node`: по краткой строке текущих показателей на каждую ноду, кроме выведенных (без топа пользователей и истории; steal, заполнение conntrack и CPU и память агента, если известны). Нагрузку за время и запас даёт `capacity_report`. |
| `node_runtime` | Только чтение | `node` (пусто = все ноды). Что нода запускает и что хочет панель: желаемые и применённые ревизия и хеш (12 символов), `in_sync`, `drift` и с какого времени, последнее применение и по каждому inbound: `enabled` (входит в желаемое состояние), `spec_version`, применённый хеш спеки, применённое и живое состояние, последняя ошибка и срок сертификата. `attention` перечисляет несостыковки: `applied_not_desired` (так выглядит «осиротевший» inbound), `desired_not_applied`, `failed`, `unknown_running`. Без адресов, пинов и ключей; к ноде не обращается. |
| `panel_logs` | Админ | Свежие записи журнала самой панели (кольцо в памяти на последние 5000, пропадает при перезапуске), новые сверху; адреса, секретные имена и значения, похожие на ключи, убраны, из атрибутов остаются только разрешённые. Фильтры: `min_level` (`debug`, `info`, `warn`, `error`; по умолчанию `info`), `minutes` (до 10080), `query` (подстрока сообщения или значения атрибута, до 100 символов, ищется в очищенном тексте), `component` (`health`, `fleet`, `http` ...), `code` (точный код ошибки), `request_id` (код, который админка показывает при сбое запроса), `limit` (по умолчанию 100, не больше 500) и `cursor` (прошлый `next_cursor`). `level`, `buffered` и `capacity` показывают, что держит кольцо. Сообщения идут из кода панели и из данных, которые она обработала: это недоверенный текст. |
| `capacity_report` | Только чтение | Насколько была нагружена каждая нода и сколько людей она ещё возьмёт: `hours` (1–720, по умолчанию 168) и необязательный `node` (только эта нода и сводка по флоту). По каждой ноде: `status` (`ok`, `busy`, `overloaded`, `unknown`, если данных нет), `bottleneck` — что кончится первым (`cpu`, `steal`, `bandwidth`, `ram`, `conntrack`, `disk`), час пик (час с самым высоким средним CPU) с его CPU и людьми, пик людей онлайн, почасовые пики CPU: 95-й процентиль (`cpu_peak_p95_pct`, самые высокие) и 75-й (`cpu_peak_typical_pct`, ниже него держится большинство часов: статус смотрит на него, и одни пики никогда не делают ноду перегруженной), p95 steal, пики conntrack и RAM, своп, диск, пики трафика против полосы ноды (`capacity_source`: заданной владельцем, иначе скорости линка сетевой карты), собственные CPU и память агента с суточным ростом, `cpu_per_100_people_pct` и `mbps_per_person` из подгонки методом наименьших квадратов по часам (`fit` говорит `few_hours`, `flat` или `no_trend`, когда по часам её не построить), `headroom_people` (сколько людей можно добавить, пока час пик не дойдёт до 80% CPU) и `recommendations` (`code`, `severity`, `params`; в `cpu_busy` поле `target` называет ноду с наибольшим запасом). `summary`: ноды по состояниям, общий запас, самые нагруженные и самые свободные ноды. Отсутствующее значение неизвестно (агент слишком старый, чтобы его сообщать), а не равно нулю. См. [Нагрузка](../guide/nodes.md#нагрузка). |
| `panel_resources` | Только чтение | Сколько сейчас стоит сама панель: её процесс (CPU в процентах машины, резидентная память, куча и вся память Go, горутины, потоки, открытые файлы против лимита, время работы), машина (занятость CPU, steal и ожидание ввода-вывода, load, RAM, своп, диск каталога данных), база (размер файла и WAL, страницы и свободные страницы; замеряется не чаще раза в минуту), агенты на связи из общего числа нод и `admin_api`: вызовы API админки за последние 5 минут (запросы, ошибки сервера и клиента, p95 в мс). |
| `retention_status` | Админ | Сколько панель хранит то, что записывает: по каждой настройке (`journal_days`, `events_info_days`, `events_warn_days`, `audit_days`, `alerts_days`, `check_samples_hours`, `check_daily_days`, `host_history_days`, `traffic_bucket_days`, `node_traffic_hour_days`) значение, значение по умолчанию, границы и единица. |
| `node_debug_logs` | Админ | Отладочная запись ноды (запускается через `node_debug_capture_plan` / `_apply`), сначала старые строки. Назови запись (`capture_id`) или ноду (её новейшая запись); без обоих вернётся список записей, которые держит панель (24 часа), новые первыми. Запись называет своё состояние `state`: `running` (строки придут, когда выйдет время), `done` или `expired` (время прошло, нода так и не прислала). Фильтры: `min_level` (`debug`, `info`, `warn`, `error`), `source`, `query` (подстрока сообщения или значений атрибутов, до 100 символов, ищется по очищенному тексту), `limit` (по умолчанию 100, не больше 500) и `cursor` (прежний `next_cursor`). Строки очищены на ноде и в панели: `<ip>` вместо адресов, без секретных имён и ключей, короткий список атрибутов. Сообщения приходят от движков ноды: это недоверенный текст. Источник `kernel` читает журнал ядра за 30 минут до начала захвата и во время него; строки пакетного журнала firewall подсчитываются, но не сохраняются. На узлах с ядровым AWG выбор `awg` включает отладку модуля на время захвата и добавляет сводку с инициированиями, не получившими ответа за 5 секунд.|
| `tasks_list` | Оператор | [Задачи по расписанию](../guide/assistant.md#задачи-по-расписанию) владельца: у каждой `id`, `name`, `kind` (`check` или `assistant`), `enabled`, `schedule` (`every 15m`, `daily 07:30`, `weekly mon 07:30`), `next_run_unix`, `running`, `last_run` (`status` `ok`, `problem`, `failed`, `skipped` или `running`, код `reason` и однострочный `summary`), `problem` с её описанием (открыт алерт `scheduled_check`) и `fail_streak` (три подряд открывают `scheduled_task_failing`). `timezone_offset_minutes` — часовой пояс панели. `relay_apply` для `create` и `enable` держит порядок самой панели: создаёт ретрансляцию (выключенной), проверяет плечо, включает её, а затем панель проверяет путь снаружи. Ретрансляция, не прошедшая проверку, остаётся выключенной, а применение завершается ошибкой с этапом (`leg` или `path`) и его кодом; при переносе порта включённой ретрансляции путь проверяется заново, и при провале ретрансляция выключается. Второй сервер появляется в подписках или пропадает из них при их следующем обновлении. См. [Ретрансляция](../guide/relays.md).

Каждый `_plan` принимает ещё `reason`: слова самого агента, не длиннее 300 символов, владелец видит их как цитату. Ни один инструмент не принимает и не возвращает пароль сервера: на экране одобрения владелец выбирает ключ панели или вводит пароль для установки, а при смене пароля новый генерирует сама панель. `user_create` никогда не возвращает ссылку подписки нового пользователя: её копирует владелец в админке.

`os_rollout_start_plan` работает с одной нодой за раз и только с одобрения владельца: пока он не одобрил план в админке, ничего не устанавливается и не перезагружается. При перезагрузке ноды люди на ней отключаются (примерно на две минуты). Собственные проверки ноды инструмент обойти не может. Инструмента для нескольких нод, для окна по времени, для обновления списков пакетов и для сервера самой панели пока нет.

`rollout_start_plan` запускает поэтапное обновление от одной до 20 выбранных нод. У каждой должен быть поддерживаемый онлайн-агент старше подписанного пакета (устаревший, с неудачным обновлением или откатившийся); новое обновление нельзя начать, пока другое выполняется или приостановлено. Панель ставит канарейкой ноду с меньшим числом людей онлайн, затем учитывает число входящих профилей; размер пакета равен одной ноде для набора меньше пяти и двум в остальных случаях. План закрепляет точный набор нод и версию/сборку подписанного пакета; если выбранная нода или пакет изменятся до применения, оно завершится ошибкой и понадобится новый план. `node_update_schedule_plan` сохраняет будущее обновление одной ноды после одобрения владельцем; при планировании нода может быть отключена, а новое расписание заменяет прежнее расписание ноды. Задание закреплено за подписанным релизом и фиксированным смещением UTC. Если в назначенное время нода отключена, панель ждёт её подключения ещё два часа, после чего задание помечается как пропущенное и само не начнётся; если подписанный пакет сменился, задание останется видимым и панель не подменит версию. Для отмены используйте `node_update_schedule_cancel_plan`. `update_timezone` влияет только на новые задания; у существующих остаются прежние момент и смещение. `update_download_timeout` меняет окно загрузки только для новых шагов: совместимые агенты получают его вместе с командой, старые сохраняют встроенный лимит, а уже начатый шаг оставляет окно, зафиксированное при отправке.

`subscription_app_upsert` и `subscription_app_remove` меняют одно приложение на странице, которую видит каждый пользователь; приложение ищется по платформе и названию без учёта регистра (если у двух приложений одной платформы одно название, план отклоняется: такие меняйте в админке). Новое приложение встаёт в конец списка. Значения проверяются так же, как при сохранении в **Подписки → Страница пользователя**: ссылка на скачивание — http(s), шаблон ссылки «добавить» начинается со схемы самого приложения (`happ://add/{url}`, `myclient://add?url={url_enc}&name={name_enc}`) или с http(s), но никогда не с `javascript:`, `data:` и подобных, только известные подстановки, не больше 30 приложений; сверх того в тексте агента не должно быть невидимых символов форматирования. План читает настройки целиком и запоминает их состояние; если до применения кто-то сохранит настройки подписок, применение откажет с «the subscription settings changed after the plan» и ничего не перезапишет: сделайте новый план. В `subscription_settings_get` и в копии плана у агента строки запроса и длинные сегменты пути ссылок показаны как `[redacted]`, как в любом результате; карточка одобрения у владельца показывает каждое значение полностью.

Telegram-прокси — один из трёх переключателей в `apps` у `user_create` и `user_update`. Пропущенное поле сохраняет значение пользователя, поэтому `{"apps": {"telegram": true}}` меняет только Telegram. Включение создаёт ключ Telegram человека, выключение отзывает его; в плане Telegram-прокси назван среди приложений. Хотя бы один из `happ` и `amnezia` должен остаться включённым: Telegram идёт в дополнение. Инструмента для самого ключа нет, и ни один инструмент не возвращает ссылки `tg://proxy`: перевыпуск и отзыв ключа и чтение ссылок делает владелец в админке ([MTProto](../guide/mtproto.md)).

Приложение Mistgate — четвёртое поле `apps` (`mistgate`, по умолчанию включено). Оно работает, только пока включён `happ`. В плане оно названо отдельным фактом `app_mistgate`, а одобрение нужно такое же, как для любого другого изменения пользователя. `client_api_settings` теперь ещё читает, у скольких людей приложение включено и сколько устройств подключено по ключу (`people`, `people_on`, `devices`).

## План и применение

Некоторые временные отказы до начала каких-либо действий оставляют план в статусе `planned` или `approved` до первоначального срока истечения; ответ содержит `busy`, код причины и время, через которое можно повторить тот же `confirm_token`. Срок плана не продлевается, успешно применённый план нельзя применить повторно, а остальные ошибки по-прежнему переводят план в `failed`.

1. Агент вызывает `<tool>_plan` с аргументами. Панель проверяет их, читает всё нужное и описывает изменение своими словами. Ничего не меняется. Результат:

   ```json
   {
     "plan_id": "pln_...",
     "summary": "Disable 5 users: their connections end and their devices are dropped from the nodes.",
     "facts": [{"key": "count", "value": "5"}, {"key": "users", "value": "...", "untrusted": true}],
     "needs_approval": true,
     "danger": ["bulk"],
     "expires_in_s": 600,
     "confirm_token": "cf_...",
     "next": "..."
   }
   ```

2. Агент показывает план человеку, на которого работает, и ждёт его согласия. Если `needs_approval` равно true, он ждёт ещё и владельца.
3. Агент вызывает `<tool>_apply` с `confirm_token` — единственным аргументом. Панель один раз выполняет сохранённые аргументы и отвечает `plan_id`, `status: "applied"` и строкой результата.

Токен подтверждения:

- срабатывает один раз, в течение 10 минут, только для того API-токена, который сделал план, и только с этим инструментом;
- не несёт аргументов: между планом и применением их не изменить;
- повторное применение уже применённого плана возвращает тот же результат; токен подтверждения другого плана, инструмента или API-токена — просто «unknown confirm token».

Если применить нельзя, ответ объясняет почему: «waiting for the owner to approve plan pln_…; it expires at …», «rejected by the owner», «expired: make a new plan», «already running», «failed: …. Make a new plan.», «the token was revoked» или «timeout, outcome unknown: check before retrying».

### Какие планы ждут владельца

План ждёт владельца, если выполняется одно из условий (список `danger`):

| Код | Значение | Инструменты |
|---|---|---|
| `step_up` | Сама операция в админке просит свежего подтверждения. | инструменты раскатки, `os_rollout_start`, `os_rollout_cancel`, `node_rollback`, `node_update_schedule` и его отмена, `node_awg_backend`, `update_timezone`, `update_download_timeout`, `retention`, `node_install`, `node_server_password_rotate`, `node_server_key_add`, `node_server_keys_add`, `node_server_key_remove` |
| `fleet` | Меняет работу нод или убирает доступ пользователей. | `node_fix`, `node_decoy`, `node_ipv6`, `relay`, `group_update`, инструменты раскатки, `os_rollout_start`, `os_rollout_cancel`, `node_rollback`, `node_update_schedule` и его отмена, `node_install`, `node_server_password_rotate`, `node_server_key_add`, `node_server_keys_add`, `node_server_key_remove`; все планы создания, обновления и развёртывания профилей |
| `bulk` | Затрагивает несколько целей в одном плане или больше 3 пользователей сразу. | массовые `rollout_start` и `node_server_keys_add`, `user_disable`, `user_reset_traffic` |
| `user_change_limit` | С этим планом токен превысит часовой лимит изменений пользователей (10, см. [«Ограничения»](api.md#ограничения)), поэтому план не отклоняется, а ждёт владельца. В карточке видно, сколько лимита использовано. | `user_disable`, `user_reset_traffic`, `user_update`, `device_revoke` |
| `traffic` | Гонит объёмный тестовый трафик между нодами. | `path_speed` |
| `user_page` | Меняет общую настройку подписки или данные, которые видят или получают пользователи. | `subscription_app_upsert`, `subscription_app_remove`, `subscription_rules_set`, `subscription_texts_set`, `subscription_link_limits_set`, `subscription_page_set`, `dns_settings_set`, `dns_preset_create`, `dns_preset_update`, `dns_preset_delete`, `node_update` |
| `schedule` | Панель будет сама, раз за разом, запускать инструменты или ассистента. | `task_create`, `task_update`, `task_delete` |

`group_update` относится к `fleet`, потому что смена профилей или отключённых нод группы может изменить доступ её участников. `group_delete` отклоняется, пока в группе есть люди. `node_update` ограничен метаданными и переключателями, которые видны в подписке; все его изменения требуют одобрения владельца, потому что API обновления ноды принимает и поля, меняющие работу ноды, которые этот инструмент не открывает.

Перед сохранением плана проверяются настройки и новые ноды. Каждое изменение профиля ждёт одобрения владельца в админке. `profile_update` и `profile_deploy` используют версию профиля, прочитанную при создании плана; если до применения версия изменилась, вернётся `changed_since_plan`. При размещении ссылки на группы объединяются с их текущим состоянием; если следующий шаг завершится ошибкой, ответ сообщит уже выполненные действия. При ошибке `profile_create` удаляет созданный профиль и входящие подключения; удаление профиля также удаляет ссылки на группы. Секреты не попадают в ответы чтения, факты и аргументы плана или записи аудита.

### Где владелец одобряет

Такой план появляется в **ИИ → Ждут вас**, а в админке загорается значок; если владелец привязал Telegram, панель ещё и присылает сообщение, что план ждёт, со ссылкой туда (решение принимается только в админке: см. [Алерты в Telegram](../operations/telegram-alerts.md)). Владелец видит изменение словами панели, пометки об опасности, причину от агента (с пометкой «Написана агентом, панель её не проверяла.») и оставшееся время, затем выбирает:

- **Одобрить** — ещё раз спросит passkey или код владельца. После этого применение агента пройдёт — только для этого плана.
- **Отклонить** — применение агента вернёт «rejected by the owner».

В `node_install` карточка одобрения показывает SHA-256 отпечаток host key, который прочитала сама панель, и тип ключа (в копии плана у агента отпечаток скрыт, как любое значение, похожее на ключ). Владелец сверяет его с доверенной копией, ставит отметку подтверждения и выбирает, как панель будет входить: **Ключ панели** (карточка показывает открытый ключ панели, он уже должен быть на сервере; выбор появляется, когда в плане назван ключ панели) или **Пароль** (владелец вводит там же SSH-пароль сервера; установка тогда по умолчанию добавляет на сервер и ключ панели, и дальше панель входит по ключу). Пока host key не подтверждён и, для пароля, пароль не введён, кнопка **Одобрить** недоступна. Панель запечатывает выбор и введённый пароль за этим планом, и применение агента, в котором только `confirm_token`, один раз запускает установку с ним и ровно с подтверждённым ключом. Пароль не проходит ни через агента, ни через его переписку, ни через провайдера модели. Смена пароля тоже требует одобрения владельца: новый пароль генерирует панель и никогда его не возвращает.

Токен никогда не может подтвердить собственный план. Нерешённые планы истекают через 10 минут после создания. **Недавние решения** хранят историю с итогом: выполнено, ошибка, истекло, отменено (токен отозвали) и так далее. Агенту не стоит проверять статус чаще раза в 30 секунд.

### Пример: добавить kl!ck для Windows и macOS

[kl!ck](../guide/client-apps.md#klck) — десктопное приложение, которое рекомендует Mistgate. Чтобы поставить его на страницу пользователя для Windows и macOS, агент с профилем «Оператор» делает так. План запоминает состояние всех настроек, поэтому каждый следующий план делайте после применения предыдущего.

1. `subscription_settings_get`: прочитать текущие приложения, чтобы знать, что там уже есть и какие записи Happ рекомендованы.
2. `subscription_app_upsert_plan` для Windows:

   ```json
   {
     "platform": "windows",
     "name": "kl!ck",
     "kind": "happ",
     "download_url": "https://github.com/vbu00/klick/releases/latest",
     "add_link_template": "klick://add?url={url_enc}&name={name_enc}",
     "recommended": true,
     "reason": "kl!ck is the recommended desktop app"
   }
   ```

   У плана `needs_approval` и пометка `user_page`. Покажите его, попросите владельца одобрить в **ИИ → Ждут вас**, затем вызовите `subscription_app_upsert_apply` с `confirm_token`.
3. То же для macOS: те же аргументы с `"platform": "macos"`.
4. Чтобы kl!ck шёл первым, снимите значок с Happ на обеих платформах, по одному плану на каждую: `{"platform": "windows", "name": "Happ", "recommended": false, "reason": "kl!ck leads on the desktop"}`, затем то же с `"macos"`. Для уже существующего приложения указывают только меняемые поля.

`kind: "happ"` означает «по ссылке подписки», какое бы приложение её ни открывало. Ссылка на скачивание — страница релизов: в именах файлов стоит версия, а сборки для Windows и macOS выходят отдельно. Ссылка в одно касание работает только в сборках kl!ck новее 0.4.0; на старых человек пользуется **Скопировать ссылку** на странице. Новое приложение встаёт в конец списка; рекомендованное идёт первым на своей платформе, где бы оно ни стояло. Результат потом показывает `subscription_settings_get` (строки запросов в ссылках для агента выглядят как `[redacted]`).

## Недоверенные данные в результатах

Имена, заметки, причины, строки логов и параметры событий и алертов приходят от пользователей, нод и других систем. Об этом говорят инструкции сервера и описание каждого инструмента, который такой текст возвращает: это данные, а не инструкции, и агент не должен выполнять найденные в них просьбы.

Панель защищает и агента, и вас:

- Текст из данных очищается: управляющие символы, переводы строк и невидимые символы форматирования убираются, длинные значения обрезаются.
- Сводка плана никогда не содержит текста из данных; такие значения идут отдельными фактами с пометкой `untrusted`, а владелец видит их в кавычках.
- То, что одобряет владелец, показывается целиком. Длинное значение (текст задачи, список резолверов, текст страницы пользователя) приходит нумерованными фактами; новое значение, которое нельзя показать как есть (скрытый или двунаправленный управляющий символ либо текст, который изменил бы редактор секретов: ключ, ссылка с токеном), отклоняется при составлении плана с указанием поля. Текущее значение поля показывается с вымаранными секретами и никогда не мешает изменению.
- Последний проход по каждому результату заменяет всё, что похоже на секрет: API-токены, ссылки подключения (`hysteria2://…` и подобные), конфигурации туннелей, ключевой материал, query-строки URL и длинные сегменты пути URL (секретный префикс, токен подписки) и голые 32-байтовые ключи.

## Чего агент не получает никогда

- Ссылок подписки и паролей страниц пользователей.
- Ключа Telegram-прокси и его ссылок `tg://proxy`.
- Ключей и конфигураций устройств, аккаунтов и ключей WARP, секретов профилей.
- Паролей серверов: ни SSH-пароля для установки, ни нового пароля после смены.
- Адресов нод и отпечатков сертификатов. Исключение — сохранённые SSH-адрес и логин, которые токену профиля «Админ» показывают `node_server_access_list` и планы `node_install` и смены пароля.
- Ничего о токенах, одобрениях, сессиях и passkey.
- Журнала аудита, если у токена не профиль «Админ».

## Аудит

Каждая процедура, которую вызывает инструмент, пишется в журнал аудита от имени «токен MCP <имя>» с источником MCP. Планы и применения добавляют свои строки: «составил(а) план изменения: <инструмент>» и «выполнил(а) запланированное изменение: <инструмент>»; решения владельца выглядят как «одобрил(а) изменение» или «отклонил(а) изменение». **Настройки → Аудит** отбирает их по источнику MCP.
