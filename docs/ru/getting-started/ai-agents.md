Это короткий операционный контракт для AI-агентов. Он ведёт к поддерживаемому установщику и не допускает попадания паролей в планы и логи.

## Для coding-агентов

Начните с [`AGENTS.md`](https://github.com/Mistgate/mistgate/blob/main/AGENTS.md) в репозитории: там карта Go-сервисов, API, генерируемого кода, тестов и требований безопасности. Не меняйте `gen/` и `web/src/gen/` вручную: редактируйте `proto/`, затем запускайте `go tool buf lint && go tool buf generate`.

Чтобы установить новую панель, следуйте инструкции [Установка панели](install-panel.md). Mistgate не требует Docker: соберите бинарники командой `make build`, поставьте `mistgate` на сервер панели и запустите через systemd.

## Для MCP-оператора

Подключайтесь к `<адрес админки>mcp` API-токеном с профилем **Админ**. Токен действует в рамках роли владельца, но опасные операции всё равно требуют одобрения в **Интеграции → Одобрения**. Используйте текущий интерфейс владельца и доверенную сборку релиза.

### Установить ноду

1. Вызовите `node_install_plan` с публичным SSH-адресом, портом, логином, именем ноды, адресом для клиентов и, если нужно, регионом и провайдером. Логин должен быть `root` или иметь беззапросный `sudo -n`.
2. Покажите данные ноды из плана и попросите пользователя одобрить его в админке. Никогда не спрашивайте пароль сервера и не передавайте его в инструменты. В карточке одобрения владелец сверяет отпечаток host key, который прочитала панель, и тип ключа, подтверждает его и вводит SSH-пароль; панель запечатывает пароль за этим планом. В копии плана у агента отпечаток скрыт.
3. После одобрения владельца вызовите `node_install_apply` только с `confirm_token`. Панель ставит ноду с паролем владельца и ровно с подтверждённым host key; пароль до агента не доходит.
4. Панель закрепляет ключ, ставит доверенного агента из подписанного набора, регистрирует ноду и ждёт её подключения. `node_server_access_list` покажет логин и адрес, но никогда не вернёт пароль.

### Сменить SSH-пароль

1. Вызовите `node_server_password_rotate_plan` с ID ноды или точным именем действующей ноды. Покажите сервер и логин, дождитесь согласия пользователя и одобрения владельца.
2. Вызовите `node_server_password_rotate_apply` только с одноразовым `confirm_token`. Новый стойкий пароль панель генерирует сама, меняет его на сервере и никогда не возвращает агенту; владелец может показать его в **Настройки → SSH-доступ** ноды после повторного подтверждения входа.
3. Перед сменой на сервере панель сохраняет зашифрованное значение для восстановления, затем проверяет новый SSH-вход и только после этого заменяет сохранённый пароль. При обрыве связи повторите процедуру: она сначала сверит текущий и ожидающий вход.

### Обновить уже подключённые ноды

Проверьте доверенный подписанный пакет и отставшие ноды через `updates_status`. `rollout_start_plan` обновляет ровно одну выбранную ноду сейчас, а `node_update_schedule_plan` запланирует её обновление на будущее по фиксированному смещению UTC в настройках панели. Для обоих действий нужно одобрение владельца. Задание закреплено за выбранной подписанной версией; отключённая нода обновится, если подключится в течение двух часов после назначенного времени, иначе задание помечается как пропущенное. Панель проверяет состояние ноды и откатывает неудачное обновление. Не переустанавливайте ноду ради обновления агента.

В [справочнике MCP](../reference/mcp.md) описаны подключение, профили токенов, срок планов, одобрения и все инструменты. Ручной способ приведён в разделе [Добавление ноды](add-node.md).
